# Applications in Python

An application can be written in Python, for logic no block covers. The API
lives in `agent_runtimes.loop.apps`, in agent-runtimes itself — no other
package to install. It uses the words of the Appspec: an *application*, its
*rules*, its *settings*, a *session*.

Three pieces:

- **`Application`** — the application: what it declares (its Appspec) and
  the code that reacts to its sessions.
- **`AppHost`** — what runs it in this process: it opens sessions and tells
  the application what the person does.
- **`Session`** — one conversation of one person with the application,
  handed to its code: to write, stream, show steps, ask, keep state, record,
  and call the application's agent. What the person sees goes through a
  **`Channel`**.

## What runs today, and what waits

Everything on this page runs **in process**, today: an application is
declared, a host opens its sessions and drives them, and its agent answers
with its rules, checks and record on. It is tested (see the end of the
page).

What does **not** exist yet:

- **A Python application of your own on a hosted runtime.** A runtime runs
  the code of the catalogue's Python examples through the
  [Session API](./session-api) — its channel the session, what it shows
  streamed as AG-UI events, what it asks answered from the page — and an
  `app.py` deployed on Datalayer runs as the spec it builds, answered by its
  agent. Your own code runs on a runtime you serve: mounted into your own
  FastAPI (see [Mounted into your own FastAPI](#mounted-into-your-own-fastapi)).
- **An agent with tools in process.** An application whose agent needs
  connections to MCP servers, skills, tools or a team runs on a runtime;
  built in this process, it is refused with the reason (see
  [The agent](#the-agent)).

## Where its code runs

**On a runtime, never in a service** (LOOP R-21). On the platform, the only
Python application code that runs is the catalogue's — its examples'
`app.py`, shipped with agentspecs — and it runs on a runtime, the sandbox a
person's agent runs in, through the [Session API](./session-api). An
`app.py` of your own is built on your machine into the spec it amounts to
(`loop apps build`, `push`); the platform keeps and runs the spec, never the
file: an application saved with an example's id and another version runs as
its agent answers, not as the example's code.

The services — ai-agents, durable — import only what reads a spec:
`load_app`, `schedule_triggers`, `session_payload`; the scheduler starts a
woken session on the runtime it launched, over HTTP (`start_session`). None
of them loads an `app.py`, builds one, or runs a session in its own process;
a test of each side keeps it so
(`test_app_code_runs_where.py` here, `test_no_service_runs_application_code.py`
in the services).

## A runnable example

A customer interview: it asks the person what they want to learn when the
session starts, answers each message through its agent inside a step, and
saves an insight from a button. The person is played by a `MemoryChannel`,
and the agent by pydantic-ai's `TestModel`, so the script runs with no key
and no network:

```python title="interview.py"
import asyncio

from pydantic_ai import Agent
from pydantic_ai.models.test import TestModel

from agent_runtimes.loop.apps import (
    AppHost,
    Application,
    ChoiceQuestion,
    MemoryChannel,
    Session,
)
from agent_runtimes.loop.apps.record import AppRecorder

# The application: what it declares is its Appspec.
app = Application(id="customer-interview", kind="chat", agent="cog-crawler:0.0.1")
app.starter("Onboarding", "Interview me about my onboarding.")
app.rule("send the summary by email", applies_to="send", behaviour="ask_first")
app.setting("tone", {"type": "string", "title": "Tone", "enum": ["warm", "dry"], "default": "warm"})
app.setting("depth", {"type": "integer", "title": "Depth", "minimum": 1, "maximum": 5, "default": 3})


# What it reacts to.
@app.start
async def opening(session: Session) -> None:
    session.state["goal"] = await session.ask("What do you want to learn?")


@app.message
async def reply(session: Session, text: str) -> None:
    async with session.step("Thinking", kind="model", input=text) as step:
        answer = await session.agent.run(text, goal=session.state["goal"])
        step.output = answer.text
    await session.send(answer.text)


@app.action("save")
async def save(session: Session, payload: dict) -> None:
    session.state["kept"] = await session.record(payload, summary="An insight")
    keep = await session.ask(ChoiceQuestion("Keep interviewing?", ("Yes", "No")))
    session.state["done"] = keep == "No"


async def main() -> None:
    channel = MemoryChannel()
    sent: list = []

    async def send(body: dict) -> None:  # the record, kept here and not sent
        sent.append(body)

    host = AppHost(
        app,
        channel,
        # A model that answers without being called: no key, no network.
        agent=lambda spec: Agent(TestModel(custom_output_text="Tell me about week one.")),
        recorder=AppRecorder(app=app.spec, send=send),
    )

    channel.reply("why people leave")            # the answer to `start`'s question
    session = await host.open(user="ada", settings={"depth": 4})
    print(session.state, session.settings)

    await host.message(session, "Hello")
    print(channel.messages[-1].author, "-", channel.messages[-1].text)

    await host.settings(session, {"tone": "dry"})
    channel.reply("No")
    await host.action(session, "save", {"insight": "pricing is unclear"})
    print(session.state)
    print([type(q).__name__ for q in channel.questions])


asyncio.run(main())
```

```text
$ python interview.py
{'goal': 'why people leave'} {'tone': 'warm', 'depth': 4}
Customer interview - Tell me about week one.
{'goal': 'why people leave', 'kept': False, 'done': True}
['TextQuestion', 'ChoiceQuestion']
```

`kept` is `False`: the application keeps no outputs in its record unless its
Appspec's `record.include` names them (see [The record](#the-record)).

The scenario is the one `agent_runtimes/tests/test_loop_app_api.py` runs
(`interview()`, `hosted()`), where the model is scripted turn by turn.

## `Application`

```python
from agent_runtimes.loop.apps import Application

app = Application(
    id="customer-interview",
    kind="chat",                       # chat, widget, decision or worker
    agent="cog-crawler:0.0.1",         # or team="…"
    name="Customer interview",         # its id in words when unsaid
    description="Interviews a customer about their onboarding.",
    instructions="Never ask a leading question.",
    model="",                          # in place of its agent's model
    goal="",                           # for a worker
    version="0.0.1",                   # optional: see below
)
```

**Its version.** Leave `version` out and the application is at `0.0.1`
while you run it here, and at **the version it is deployed as** on the
platform: the version the Studio stored is the authority, and a code that
says no version of its own takes it (`app.declared_version` is `None`). Say
a version — `version=` here, or `version:` in the spec `Application.from_spec`
reads — and the runtime checks it: a deployment of `0.0.4` whose code says
`0.0.2` is refused, *The code says it is customer-interview 0.0.2, not 0.0.4
the agent runs: its code and its Appspec are of different versions.* Code of
another application is refused whatever its version.

Or attach code to an Appspec that already exists — read from its YAML, or as
an `AppSpec`:

```python
app = Application.from_spec(spec)
```

### Declarations: plain calls

What an application declares is its Appspec. Each call adds to it:

| Call | Declares |
| --- | --- |
| `app.starter(label, message, *, category="", profile=None)` | A first message offered to the person, under its `category` when it has one (LOOP P-20): the starters of a category together, under its name, those without one first. With `profile`, it is that profile's, offered in place of the application's. |
| `app.profile(id, label, *, description="", instructions="", model=None)` | One of several assistants in one application (LOOP P-20): two at least, or none. The person picks one before the conversation starts — the first unless they pick another — and keeps it to the end: its `instructions` are told to the agent in every run, its `model` is run in place of the application's (a mode's model wins over it), its starters offered. `session.profile` says it. |
| `app.setting(name, field, *, required=False, widget=None)` | A setting of the session: a field of the settings' form (LOOP C-16), `interface.settings`, the JSON Schema of an object of named fields. `field` is the field's own schema — a `type`, the `title` the person reads, a `default`, and what it takes (`enum`, `minimum`, `maximum`…). `widget` is the input it is drawn with when not its field's own (`interface.settings_ui`, LOOP P-20) — see [The nine inputs](#the-nine-inputs). Drawn with `@datalayer/primer-rjsf` beside the conversation and on a deployment's Ship card. A field that is not a schema raises `TypeError`; the old `app.setting(id, type, label, …)` is gone. |
| `app.translation(language, words)` | What a person reads of it in another language (LOOP P-26), by BCP 47 tag: `words` keyed as `interface.translations` are — `name`, `description`, `welcome`, `starters` by label, `categories`, `settings` by field, `commands` by name, `modes` and `profiles` by id. The page shows the person's language when it has it, else its own words. |
| `app.rule(action, *, applies_to, behaviour)` | When it acts alone and when it asks: `applies_to` names classes of action (`send`, `write`…) or tools (`server.tool`); `behaviour` is `do_it`, `if_asked`, `ask_first` or `leave_to_me`. |
| `app.connection(server, *, access="read", acts_as="owner", only=())` | An MCP server it reaches, read or write, in the owner's or the person's name, limited to the tools `only` names. |
| `app.command(name, description, *, prompt="")` | A slash command in the composer (LOOP P-19): typing `/` lists it, picking it sends `prompt`, `{input}` the words typed after it. Without a prompt, used as a decorator, its code answers it — see below. |
| `app.mode(id, label, options, *, default=None)` | A mode switch beside the composer: `options` are two at least, each `{id, label, description?, instructions?, model?}`. The option the person picks goes with every run: `session.modes[id]` says it, and `session.agent` is told its `instructions` and runs on its `model`. |
| `app.ui.<component>(id, **properties)` | A component of the catalog on its surface, typed: `app.ui.table("runs", columns=["model"], rows={"path": "/runs"})`. One method per component (`table`, `chart`, `form`, `text_field`…), its properties typed from the catalog's JSON Schema and checked against it; `app.component(id, "Table", **properties)` is the same, untyped. See [typed calls](../agentspecs/ui-plugins#typed-calls-from-python). |

#### The nine inputs

A setting is drawn with one of nine inputs (LOOP P-20), each a JSON Schema
field and, where needed, the `widget` that draws it — the setting's
`ui:widget` in the Appspec's `interface.settings_ui`:

| Input | `field` | `widget` |
| --- | --- | --- |
| Select | `{"type": "string", "enum": [...]}` | — |
| Slider | `{"type": "integer", "minimum": 1, "maximum": 10}` | `"range"` |
| Switch | `{"type": "boolean"}` | `"switch"` |
| TextInput | `{"type": "string"}` | — or `"textarea"` |
| Checkbox | `{"type": "boolean"}` | — |
| DatePicker | `{"type": "string", "format": "date"}` | — |
| MultiSelect | `{"type": "array", "uniqueItems": True, "items": {"type": "string", "enum": [...]}}` | — or `"checkboxes"` |
| RadioGroup | `{"type": "string", "enum": [...]}` | `"radio"` |
| Tags | `{"type": "array", "items": {"type": "string"}}` | `"tags"` |

```python
app.setting("seats", {"type": "integer", "title": "Seats", "minimum": 1, "maximum": 50}, widget="range")
app.setting("live", {"type": "boolean", "title": "Live data"}, widget="switch")
app.setting("topics", {"type": "array", "title": "Topics", "items": {"type": "string"}}, widget="tags")
```

A widget that cannot draw its field is refused when the spec is read: a
slider without a `minimum` and a `maximum`, a switch for a string.

#### Profiles

```python
app.profile("support", "Support", instructions="Answer from the documentation, briefly.")
app.profile("sales", "Sales", description="Plans and prices", model="anthropic:claude-sonnet-4-5-20250514")
app.starter("Pricing", "What does the Business plan cost?", category="Plans", profile="sales")
app.translation("fr", {"profiles": {"sales": {"label": "Ventes"}}, "starters": {"Pricing": {"label": "Tarifs"}}})

@app.message
async def reply(session: Session, text: str) -> None:
    answer = await session.agent.run(text)  # told the profile's instructions
    await session.send(f"[{session.profile}] {answer.text}")
```

The page offers the profiles in a picker beside the composer and sends the
one picked with every run (`forwardedProps.loop.profile`); the empty chat
offers its starters. Once the first message is sent, the conversation keeps
its profile: a run naming another is refused (409, *This conversation is with
Sales: start another to talk to Support.*), and one naming a profile the
application does not have too (422).

`app.spec` is the Appspec they amount to, **validated** as any Appspec is:
an application that would not run raises `AppNotRunnable` with its reasons,
in sentences. `app.document` is the same as a plain dict, as its YAML would
say it.

### Reactions: decorators

What an application reacts to, one handler per moment — sync or async, the
session always first:

| Decorator | Called with | When |
| --- | --- | --- |
| `@app.start` | `(session)` | A session starts. |
| `@app.message` | `(session, text)` | The person writes. Without a handler, the application's agent answers, streamed. |
| `@app.action(name)` | `(session, payload)` | The person presses the button of that name. The values a `Form` sends with it are checked against its schema first: refused, the handler is not called (`ValueError`, or 422 from the [Session API](./session-api)). |
| `@app.file` | `(session, files, text)` | The person sends files with a message without being asked (LOOP P-21): the `UploadedFile`s, and the words sent with them. Which kinds and sizes may be sent is the Appspec's `interface.uploads`; the runtime refuses the rest before this runs. Without a handler, the words go to `message` and the files wait for what the code asks. See [What a person sends](#what-a-person-sends). |
| `@app.settings` | `(session, settings)` | The person changes settings; given all of them, checked. A change made on the page goes with the next message, and this runs before that message's handler (LOOP P-20). |
| `@app.window` | `(session, data)` | The page the application sits in posts a message (LOOP P-25): `element.postWindowMessage(data)`, on your own server. See [Window messages](#window-messages). |
| `@app.stop` | `(session)` | The person presses Stop, after what was running is cancelled. |
| `@app.resume` | `(session)` | An earlier session is reopened, its state back — an ended one too. |
| `@app.feedback` | `(session, feedback)` | A person gave a thumb up or down on an answer, with a comment or not, and it is kept in the record (only when the Appspec's `record.include` names `feedback`). `feedback` is a `Feedback`: `liked`, `comment`, `message` (the answer it is about, `answer-<n>`) and `by`. See [Threads and feedback](#threads-and-feedback). |
| `@app.end` | `(session)` | The conversation closes for good, after what was running is cancelled: the person left the terminal, or a client ended the session. The last thing it runs; nobody reads what it sends. |
| `@app.logout` | `(session)` | The person signed out. The session then ends: `end` runs after it. |
| `@app.command(name, description)` | `(session, words)` | The person sends `/<name> words`: the code answers in place of `message`. Declared in the Appspec with the prompt `/<name> {input}`, and marked as code by `loop apps build` (`command <name>`); in the terminal, `/<name>` runs it too. |
| `@app.schedule(cron, *, description="", prompt="")` | `(session)` | On a schedule, in a session of its own. Also adds the schedule to the Appspec's triggers. |
| `@app.page` / `@app.page(live=False)` | `([session], **inputs)` | A widget's page (LOOP P-05): its inputs changed on the page, or Run pressed with `live=False`. Returns its outputs. See [A widget's page](#a-widgets-page). |

A second handler for the same moment, action or schedule raises
`ValueError`.

### A widget's page

A widget can be a function of its inputs, like a notebook cell with sliders
(LOOP P-05): its page draws the inputs as a form and the outputs below them,
and as an input changes, the function runs again on all of them and the
outputs change in place — no message, no conversation, on the same page and
renderer as a chat application.

```python
from typing import Literal

from agent_runtimes.loop.apps import Application

app = Application(id="quote", kind="widget", agent="jupyter-data-analyst:0.0.1")
app.output("total", title="Total")
app.output("lines", "Table", columns=["item", "amount"])
app.input("seats", {"type": "integer", "title": "Seats", "minimum": 1, "maximum": 1000, "default": 10})


@app.page
def quote(seats: int = 10, plan: Literal["Team", "Business"] = "Team") -> dict:
    price = 12 if plan == "Team" else 30
    return {
        "total": f"{seats * price} €",
        "lines": [{"item": plan, "amount": seats * price}],
    }
```

**Inputs** are the function's parameters, by name: each typed by its
annotation — `int`, `float`, `bool`, `str`, a `Literal` or an `Enum` of them,
a `list` of them — its default its default, one without a default required.
`app.input(name, field, required=False)` says one more precisely (a title, a
minimum, a maximum), as `app.setting` does; the field it says wins. Together
they are a form (LOOP C-16), drawn on the page at `/inputs/<name>`. The
function takes the session first when it wants it (`session.agent`,
`session.state`), and `**inputs` to take inputs it does not name.

**Outputs** are declared with `app.output(name, component="Text", *,
title="", **props)`: `Text` shows words (a number is shown as words),
`Image` an address (a URL or a data URL), `Table` rows and `Chart` points —
each a list of records, a pandas DataFrame too — the component's other
properties checked against the catalog as `app.ui` checks them (a Table's
`columns`, a Chart's `kind`, `x` and `y`). The function returns the value of
its one output, or its outputs by name, all of them. Declaring none, the page
has one: `result`, in words.

Both are its Appspec's `interface.page` — `function`, `inputs`, `outputs`,
`live` — so that the Canvas shows them and validation runs them; `loop apps
build` marks the function as code (`# loop:code page: quote (app.py:9)`).

| What | Refused |
| --- | --- |
| Declaring | `app.output` with another component (`ValueError`), properties its schema refuses, or a name used twice; `app.input` of what is not a JSON Schema, or of an input the function does not take (`TypeError`); a parameter of a type a form does not ask, or taken by position (`TypeError`); `app.action("page")`, the action that runs the page; a page on an application that is not a widget, or inputs declared and no `@app.page` (`AppNotRunnable` from `app.spec`). |
| Running | Inputs its form refuses — out of range, not one of its options, an input it does not have — in a sentence (`ValueError`; 422 from the [Session API](./session-api)); what it returns when an output is missing or unknown, or a value its component does not draw. |

`AppHost.page(session, inputs)` runs it in process and returns its outputs;
the page sends its inputs as the `page` action of its session
(`{"inputs": {...}}`), and the outputs come back as a `loop.page` event. The
terminal says them. `loop apps validate app.py --tests --local` runs the page
on its inputs' defaults — *It shows each of its outputs for its inputs'
defaults.* — and fails when the function raises, returns what its page does
not show, or an input it requires has no default (a page shows its outputs
from the start).

### Code where plain words are not enough

A rule, a test in words, a catalogue check say most of what an application
needs. Where they cannot, its code says it (LOOP P-06) — and declares it in
its Appspec, so that the Canvas shows it (*What its code decides*: its tool,
its check, its test, each with the line that decides it) and validation runs
it:

```python
from agent_runtimes.loop.apps import Application, Conversation

app = Application(id="order-desk", kind="chat", agent="worker-support:0.0.1")
app.rule("Refund an order", applies_to="refund", behaviour="ask_first")


@app.tool(does="read")
def lookup_order(number: str) -> dict:
    """Find an order by its number."""
    return ORDERS[number]


@app.tool(does=["write", "buy"])
async def refund(number: str, amount: float) -> str:
    """Refund an order."""
    return await PAYMENTS.refund(number, amount)


@app.check("answer")
def no_prices(text: str) -> str | None:
    """It never quotes a price."""
    return "It quoted a price." if "$" in text else None


@app.check("tool_call", description="Refunds stay under 100.")
def small_refunds(tool: str, arguments: dict) -> bool:
    return tool != "refund" or arguments["amount"] < 100


@app.test("It gives the order's status", ask="Where is order 42?")
def gives_the_status(conversation: Conversation) -> bool | str:
    return "shipped" in conversation.answer or "It did not say the status."
```

| Decorator | Declares in the spec | Runs |
| --- | --- | --- |
| `@app.tool(does=…, description="")` | `tools`: its name (the function's), its description (the docstring's when unsaid), its `parameters` — the JSON Schema of its arguments, from their types — and what it `does`, by class of action. | Its agent is given it beside its own tools; sync or async, called with its arguments, what it returns is what the agent reads. Every call is decided by the rules, as any tool's: by a rule that names it by its name alone (`applies_to="refund"`), else by what it does — reading needs no rule, anything that acts asks first. |
| `@app.check(on, description="")` | `checks.code`: its name, its stage, what it checks in words (the docstring's first line when unsaid). | At its stage, after the built-in checks and before the record: `answer`, `handler(text)` before the answer is given — refused, the agent is asked again with why; `tool_call`, `handler(tool, arguments)` once the rules let the call through — refused, the call is stopped (`AppCheckBlockedError`). `None` or `True` lets it pass, `False` or a sentence refuses; anything else raises. Each refusal is a `check` entry of the record. |
| `@app.test(expect, *, ask)` | A case of `tests.cases`, its `code` the function's name. | `loop apps validate app.py --tests --local`: the case asked of the application in this process, a session of its own, and its `Conversation` — `ask`, `answer` (its messages, one after the other), `messages`, `steps`, `asked` (what it stopped to ask the person, when it did) — handed to the function, which returns `True`, `False` or a sentence saying why it failed. `None` is not a pass: it is said, and the test is not run. Without the file — on Datalayer, through the Evals engine — the case is judged by its words. |

`@app.tool` without `does` raises `TypeError`; a tool or a check that says
nothing of itself, a stage that is neither `answer` nor `tool_call`, or a
name used twice raise `ValueError`; what agentspecs refuses — a class of
action that is none — raises `AppNotRunnable` from `app.spec`.

`loop apps build` marks each as code, `# loop:code tool lookup_order:
lookup_order (app.py:7)`, `check …`, `test …`. A spec validated alone — its
`app.yaml` without the file — *needs attention* for each: its tools are not
given, its checks check nothing, its tests are judged by their words.

```bash
loop apps validate app.py --tests           # lists them
loop apps validate app.py --tests --local   # runs them here; exit 1 when one fails, 3 when one could not run
```

### Schedules on the platform

A deployed application's schedules fire with nobody at a browser. When an
application is deployed, each `schedule` trigger of the deployed version is
registered with the platform's scheduler; on each tick the scheduler
launches a runtime — named for the application and the deployment, so its
time is counted against them on Usage — creates the application's agent on
it as the hosted page does, opens a session of it on the
[Session API](./session-api) said to be woken by that schedule, and stops
the runtime. The session runs the schedule's handler, or asks the agent the
trigger's `prompt` (its `description` when it has no prompt). Pausing the deployment stops its schedules,
resuming starts them again, taking it down removes them; deploying another
version registers that version's schedules. Every tick is a run of the
schedule, which says whether it answered.

Your code travels with the deployment. The `app.py` that `loop apps push`
kept beside the version's spec is what the platform hands the runtime on
each tick (`app_code` on the payload that creates the agent), and the
runtime runs the session with it — its `start`, `message` and `schedule`
handlers, its tools and checks — under the application's rules, as
`loop apps run` does. The runtime accepts code for a deployment's agent
only, once it holds the deployment's principal token: a request carrying
code with no deployment behind it is refused. A version written as a spec
carries no code, and its agent is asked the prompt. The stream of a woken
session ends only once its turn is on the record, so a scheduler that stops
the runtime as the stream ends loses nothing of it. A tick run by your code
is recorded as an agent's run is: the run, its turn — the trigger's prompt
and what your handler sent — and its output, beside the steps it took,
as far as the Appspec's `record.include` keeps them. Each tick reserves a
bounded amount of credits for its runtime — the deployment's spend limit
when its owner set one, else the platform's own small reservation — never
a share of what the owner has left.

A deployment kept **always on** runs your code too. Its version's `app.py`
is kept with the deployment as it is deployed or moved to another version,
beside its spec, and the runtime it is kept on is handed it each time it
starts — `app_code` on the payload that makes its agent there
(`kept_payload`), also when the platform starts it again with nobody
present, which reads no Spacer item. Every session of that agent — a
visitor's at the address, a tick's — runs with it. A deployment kept
before its code was kept with it is not guessed to have none: it stops
being kept on, saying it is to be deployed again.

**A `@app.schedule` handler runs on the tick** when the runtime runs the
application's code — an `app.py` of the catalogue, at the version the
runtime has: the scheduler knows a schedule by its position among the
application's triggers, the runtime finds the handler the code declared
there (`app.schedule_at(position)`) and runs it with the session, in place
of the prompt, as a command's code runs — what the registry holds for
`loop.app.schedule` under `<id>/<name>` (`AppHost.scheduled(session, name)`).
The code's `start` runs first, as in any session opened. A schedule the
code did not declare — one of the Appspec's own — asks the agent its
prompt. When the trigger at that position is not the schedule the code
declared (another cron: code and Appspec of different versions), the
session is refused and the tick fails, saying so. An `app.py` of your own
is built into its spec, and the spec is what runs: its handlers run where an
`AppHost` runs them (`host.schedule(name)`), not on the tick.

Woken, nobody is present: the session only reads unless one of the
application's rules says otherwise (see *With nobody present* in the
[app renderer](./app-renderer)) — its handler's `session.agent` and its
agent alike. A handler that asks somebody something (`session.ask`) ends
the tick as waiting: nobody is there to answer.

A schedule with neither a prompt nor a description is refused at deploy: a
session woken with nothing to ask does nothing. An application run by a
team is not woken yet.

The record of a session nobody opened says what woke it: `woken_by`,
`{"kind": "schedule", ...}` — the schedule, its cron, and on the platform
the scheduler's run — sent with its entries and written on its first.

### In whose name it acts on the platform

A deployed application acts as itself: its **service principal**, made at
its first deploy, with a token narrowed to what the version it runs was
granted — never with the token of the person who launched the runtime.

- **What it may reach** is read from the deployed version's Appspec — each
  connection (its server, `read` or `write`, in whose name, its `only`), each
  Space, and the parts of its computer turned on — and kept by the platform
  as the deployment's grant (RFC 9396 `authorization_details`). An
  application granted nothing has an empty list, and reaches nothing.
- **Its token.** The agent of a deployment is created on a runtime with
  `app_instance.deployment_uid` and the token of whoever opens its session
  (the hosted page, the scheduler's tick). The runtime asks ai-agents for the
  principal's token with it (`POST /api/ai-agents/v1/apps/deployments/{uid}/principal-token`)
  before the agent is made, keeps it in memory by deployment
  (`agent_runtimes.loop.apps.principal`), and asks again, with the latest
  request's token, when less than five minutes of its hour are left.
- **What it is used for**: the agent's model calls through ai-inference
  (metered on the application's owner, naming the deployment and the
  principal), the Datalayer MCP gateway, and the session's record. The
  runtime's inference token and `DATALAYER_USER_TOKEN` are never used in its
  place.
- **Fail fast.** Without the token the agent is not created (422, in a
  sentence); once it has expired the agent calls nothing and says so, and a
  chat request is answered 403.
- **Withdrawn, at once.** Every service reading the token asks whether its
  grant still stands, and remembers the answer ten seconds. Moving the
  deployment to a version granting less, pausing it, taking it down or
  deleting the application revokes the grant, so the token stops being
  honoured within ten seconds, not at its expiry.

A Preview, a test run and an agent no application runs keep the runtime's
own inference token: they are a person trying something, not a deployment
acting alone.

**A Preview is held to the same Space grants** (LOOP R-25): though it runs as
the person trying it, the tools of its session reach only the Spaces its
Appspec grants (`permissions.spaces`), each as far as it says — what is tried
is what ships. The runtime asks ai-agents, with the person's token, for a
token of theirs narrowed to those Spaces
(`POST /api/ai-agents/v1/apps/{app_uid}/preview-token`, minted by IAM for an
hour, only for an owner or editor of the application), keeps it beside the
principals' and renews it the same way; its runs carry it in place of the
person's (see [Session API](./session-api)). An Appspec granting no Space
reaches none. Its model calls do not change.

### Its notifications

An Appspec's `notifications` names where an approval reaches a person —
`email`, `slack`, `teams` — and those are the channels the runtime sends
through for the application's sessions (`agent_runtimes.loop.apps.notifications`).
Its agent's own `notifications` are not used: an application's agent is
given no `send_notification` tool.

- **When.** Each time a rule (*Ask me first*, *Do it if I asked*) or a Gate
  asks a person through the tool-approval path — where nobody may be
  watching — before the question waits. A question asked in the session
  itself (the terminal, `session.ask`) is not notified: the person is there.
- **How.** The runtime asks ai-agents, once, with the channels the
  catalogue offers (`POST /api/ai-agents/v1/apps/notifications`, event
  `approval.requested`). ai-agents mails the account's own address through
  Datalayer's mail, and posts to the Slack incoming webhook that account
  keeps among its secrets as `SLACK_WEBHOOK_URL`.
- **As whom.** A deployment asks with its principal's token, so what is sent
  reaches the application's **owner**, in the owner's channels (the
  principal may read that one secret of its owner's, by name, and no other).
  A Preview asks with the person's token: it reaches the **person trying
  it**, in their own channels, and nobody else.
- **Never silent.** A channel Datalayer does not offer (Teams today) is
  refused before anything is sent, in the sentence the Studio's setup states
  say; an account with no address, no `SLACK_WEBHOOK_URL`, or a webhook that
  refused comes back from ai-agents with its sentence. Every channel's
  outcome — `sent`, `refused` or `failed` — is written to the record as a
  `notification` entry, whatever `record.include` says, and logged when it
  was not sent. Sending never stops the question it is about.

### Approved in advance

A rule that says `if_asked` — *Do it if I asked* — acts only on what the
person approved before, and asks otherwise
(`agent_runtimes.loop.apps.grants`). Never from a model's reading of the
conversation.

- **What an approval is.** Given by the person in the Studio — *send replies
  to my team, until Friday* — and kept by IAM as a grant of theirs: the
  application, one action (`send`, `buy`, `delete`, `publish`, `write`),
  whom it reaches (addresses, `@domain`s, `#channel`s; none for anyone),
  their words, and an end at most 90 days away. They read it back and
  revoke it there; it mints no token.
- **What it covers.** A call of that application whose classes are that
  action, or that action and reading — an approval to send never covers a
  tool that sends and deletes — and, when it names recipients, every
  recipient the call's arguments name (`to`, `cc`, `bcc`, `recipients`,
  `attendees`, `channel`…) is one of them. A call naming nobody is not
  covered by an approval that names somebody.
- **Where it is read.** At the tool call, before the person would be asked,
  from `GET /api/iam/v1/oauth/task-grants/approvals/standing?app_uid=`, with
  the token the application acts with: a deployment's principal's (IAM
  answers its owner's approvals, for that application only), else the
  person's whose Preview it is. Answers are kept ten seconds, so a revoke is
  honoured within them. Approvals that cannot be read are none: the person
  is asked, and the record says why.
- **What is recorded.** The `decision` entry of a call done because of an
  approval names it (`approved_in_advance`, `approved_words`).
- An application the platform does not know (no `app_uid`, a local run)
  has no approvals: `if_asked` asks, as `ask_first` does.

Every approval the runtime asks for carries, beside the call's arguments,
the rule or Gate it was asked under (`_rule`, `_check`) and the application
(`_app`, and `_app_uid` when the platform knows it), so its own page, the
Tool Approvals page and its channels say whose it is.

## `AppHost`

`AppHost(app, channel, *, agent=local_agent, recorder=None, registry=None)`
runs an application in this process. A runtime, a test or a script drives it:

| Method | Does |
| --- | --- |
| `await host.open(user=None, settings=None)` | Opens a session and runs `start`. Returns the `Session`. |
| `await host.message(session, text)` | Runs `message`, or lets the agent answer. |
| `await host.action(session, name, payload=None)` | Runs the action; an unknown one raises `KeyError`. |
| `await host.files(session, files, text="")` | Runs `file` with the files sent without being asked; without one, the words go to `message`. |
| `await host.window(session, data)` | Runs `window` with what the page posted; without one, raises `KeyError`. |
| `await host.settings(session, values)` | Checks the values against the settings' form, keeps them, runs `settings`. A field the form does not have, or a value its schema refuses, raises `InvalidAnswer` (*“Its settings” was sent what its fields refuse: depth: 9 is greater than the maximum of 5.*). |
| `await host.stop(session)` | Cancels what runs in the session, then runs `stop`. |
| `await host.resume(session_id, state, user=None, settings=None)` | Reopens a session with its state, and runs `resume` — an ended one too. |
| `await host.end(session)` | Cancels what runs in the session, runs `end`; the session then takes nothing more — a message, an action, settings or Stop raise `ValueError` (*Session … has ended.*). Ending it again does nothing. |
| `await host.logout(session)` | Cancels what runs, runs `logout`, then ends the session. |
| `await host.schedule(name)` | Runs a schedule now, in a new session whose record says the schedule woke it. |
| `await host.scheduled(session, name)` | Runs a schedule's handler in a session already open — the one a tick woke on a runtime. |

Each handler runs as one turn: it can be stopped, and the record of the turn
is sent when it ends. `agent` says how the application's agent is built
(`local_agent` unless said); `recorder` where its record goes (to the
platform unless said).

`load_application(path)` returns the one `Application` an `app.py` defines;
a file with none, or more than one, raises `ValueError`.

### A Reactor plugin

An application written in Python is a [Reactor](/apps) plugin, as one
written as a spec is: `loop-app-<id>`, its manifest the application's
identity (name, version, description, emoji, kind) — the name its page's
plugin has too, which the manifest names as what it cannot be used without
(`frontend_dependencies`), both delivered as one extension of that name
([one application, two plugins](./app-renderer#one-application-two-plugins-of-one-name)).
`loop apps eject` changes nothing of it: the `app.py` it writes is the same
pair as the spec it was written from. Each decorator is a
contribution of that plugin to a point of its own — `loop.app.start`,
`loop.app.message`, `loop.app.settings`, `loop.app.stop`, `loop.app.resume`,
`loop.app.end`, `loop.app.logout`, and `loop.app.action` and
`loop.app.schedule` known as `<id>/<name>` — beside its spec on `loop.app`.

An `AppHost` loads the application so (`register_application`) into its
`registry` — one of its own unless given — and calls what the points hold
(`reaction_of`): a later contribution to the same moment of the same
application, another plugin's, answers in its place, and is gone when that
plugin is disposed. `host.dispose()` takes the application's plugin away —
its spec and every reaction; an action then raises `KeyError`. `loop apps
run` and a runtime's [session](./session-api) load it the same way, each
session's host with its own registry.

```python
from reactor import ContributionRegistry, PluginContributions
from agent_runtimes.loop.apps.plugins import REACTION_POINTS

registry = ContributionRegistry()
host = AppHost(app, channel, registry=registry)

async def louder(session, text):
    await session.send(text.upper())

PluginContributions(registry, "shouting").contribute(
    REACTION_POINTS["message"], louder, contribution_id=app.id
)  # answers in place of app's own @app.message, until disposed
```

## `Session`

A session is made by the host and handed to the application's code — never
made by that code.

| | |
| --- | --- |
| `session.id` | The session's id: its conversation and its record. |
| `session.user` | Who the person is, when the host knows: embedded with `user: signed`, the `sub` the host's server signed (LOOP D-21). |
| `session.state` | A dict the application keeps across the turns of this session; each session has its own. |
| `session.settings` | The person's settings, by id, their defaults filled in; a copy. |
| `session.profile` | The id of the profile the conversation is with (LOOP P-20): the first unless another was picked; `None` for an application without profiles. |
| `session.app` | The application, as its Appspec says it. |

### Writing to the person

- `await session.send(text, author=None)` — a message, by the application's
  name unless said. Returns the `Message`.
- `await session.stream(tokens, author=None)` — a message as it comes,
  piece by piece, from any iterable or async iterable of strings; each piece
  is delivered as a `Delta`, then the whole `Message`.
  `await session.stream(session.agent.stream(text))` shows the agent's
  answer as the model writes it.

### What an answer shows

An answer shows more than text: the components of the catalog — the ones the
Canvas places and `app.ui` places on the application's surface, checked
against the same JSON Schema. `session.ui.<component>(id, **properties)`
makes one, typed:

```python
await session.send(
    "Three runs, cheapest first.",
    show=[
        session.ui.table("runs", columns=["model", "cost"], rows={"path": "/runs"}),
        session.ui.chart("costs", kind="bar", x="model", y="cost", points={"path": "/runs"}),
        session.ui.image("plot", url="https://example.com/plot.png"),
    ],
    data={"runs": runs},
)
```

- `show` — components, drawn under the text in the order given; a component
  another names as its child (a Button's label) is drawn where that one puts
  it. Text, Image, Table, Chart, Button, Card, Row, Column, a file to
  download and the rest of the catalog.
- `data` — what a property bound to a path reads (a Table's `rows`, a
  Chart's `points`): the answer's own data.
- A Button's action (`action={"event": {"name": "again"}}`) is sent to the
  application when it is pressed, by name, with what it read: its
  `@app.action("again")` reacts, as to a button of its page. A form's
  submission on any other surface stays the agent's next message.
- `send`, `stream` and `update` take both; `update` keeps what the message
  showed unless told, and `show=[]` takes it away.
- A component the catalog does not have, properties its schema refuses, two
  components of one id or a child no component is raise `ValueError`, in a
  sentence, before anything is sent.

**A file to download** is `session.ui.download`: the name it is saved as and
where it is — an `https://` link, or the file itself as a `data:` URL — with
its kind and size said beside its name and a line under it. Pressing it
saves the file; an `action` on it is sent to the application as a button's
is. Any other link (`javascript:`, a path of the runtime) is refused by the
schema before anything is sent.

```python
import base64

csv = "month,total\nJan,1200\n".encode()
await session.send(
    "Your export.",
    show=[
        session.ui.download(
            "totals",
            name="totals.csv",
            url="data:text/csv;base64," + base64.b64encode(csv).decode(),
            media_type="text/csv",
            size=len(csv),
            description="The month's totals.",
        )
    ],
)
```

A `data:` URL travels with the message: keep it to files of a few megabytes,
and give a link for anything larger.

On the channel, they are the `Message`'s `components` and `data`. Over the
[Session API](./session-api) they are a surface under the message, drawn by
the chat's A2UI renderer — the one a team's answers are drawn with on the
home page; a terminal names each (*▣ Table runs*, *▣ Download totals: totals.csv*).
**On the record**, what an answer showed is kept with it, under `outputs`
(`record.include`): each component by its kind, its id and the words it
shows — a title, a label, a file's name — and the names of its data, never
the data itself.

### Where an element shows

An element — components of the catalog, as an answer shows them — shows
where it belongs (LOOP P-18): in the conversation, in a side panel beside
it, or on a page of its own over it. Its code opens it, changes it and
closes it:

```python
panel = await session.show(
    session.ui.table("runs", columns=["model", "cost"], rows={"path": "/runs"}),
    where="panel",
    title="Runs",
    data={"runs": runs},
)
await panel.update(data={"runs": runs + [latest]})   # changed in place
await panel.close()                                  # or session.close(panel.id)

await session.show([session.ui.text("intro", text="The report"), ...], where="page", id="report")
await session.close("report")
```

- `where` — `inline` (the default): a message of the conversation, carrying
  it, its title the message's text; `panel`: the side panel on the trailing
  edge, several stacked in the order they opened; `page`: a page of its own
  over the workspace, the last opened shown.
- `title` — over it; the application's name when unsaid. `id` — what the
  code names it by; a new one when unsaid. Shown again under the same `id`,
  it is changed in place; one open elsewhere is refused (`ValueError`):
  close it first.
- `data` — what its components bound to a path read, as an answer's.
- A Button on it sends its action to `@app.action`, as an answer's does.
- `session.elements` — what is open now, by id. Closing one that is not
  open raises `ValueError`.
- The person closes a panel or a page on their screen with its own button;
  the code is not told, and may show it again.

On the channel, a panel or a page is a `Shown` event, delivered again when it
changes, and `Closed` when it goes (`MemoryChannel.shown` is what is open);
inline, it is a `Message`. Over the [Session API](./session-api) it is a
`loop.element` event, drawn by the `app-elements` plugin every application's
workspace mounts; a resume draws again what was open, and its code can still
close it. A terminal cannot open one: it names it (*▸ Runs, shown in the
side panel*) and its components.

### Components of your own

When the catalog has no component for what you want to show — a gauge, a
map, a diagram — write one (LOOP P-17). It is a component of this
application only: its Canvas places it, its page draws it, its code shows it
inline, in a panel or on a page, and a widget's page draws an output with it.
No other application sees it.

```python
app.custom_component(
    "Gauge",
    description="A dial, from nothing to its most.",
    source="https://elements.example.com/gauge.js",   # a built ES module
    integrity="sha384-…",                               # the module reviewed
    props={
        "type": "object",
        "properties": {"label": {"type": "string"}, "most": {"type": "number"}},
        "required": ["label"],
    },
    shows=["value"],      # bound to what the application publishes
    sends=["chosen"],     # written, then its action dispatched
)

app.component("load", "Gauge", label="Load", value={"path": "/load"})   # on its surface
app.output("load", "Gauge", title="Load", label="Load")                 # a page's output

await session.show(session.component("now", "Gauge", label="Now", value=42), where="panel")
```

- It is declared in the spec, under `interface.custom_components`, and
  reviewed as a component of the catalog is: agentspecs refuses a name of the
  catalog's, a property of a type the renderer cannot tell apart, a binding
  that is also a property, an example its schema refuses, and a module that
  is not a built ES module over `https://` (or `http://localhost` while you
  write it). Where it is used, its properties are checked against its schema
  — by `app.component`, `session.component`, `session.show` and the page.
- `session.component(id, component, **props)` makes a node of the catalog or
  of the application's own; `session.ui` keeps the catalog's typed calls.
- On a widget's page, its value is what it shows first (`shows[0]`): any
  value JSON writes, a DataFrame its rows.
- The module's default export draws it into the element it is given:

  ```js
  export default function draw(root, { props, send }) {
    const dial = document.createElement('meter');
    root.append(dial);
    const update = next => { dial.max = next.most ?? 100; dial.value = next.value ?? 0; };
    update(props);
    dial.onclick = () => send('chosen', dial.value);
    return { update };
  }
  ```

  A React component is bundled into such a module with its React; a module
  of the application's folder, built and served with it, is LOOP P-29.
- It runs in a sandboxed frame of no origin (`sandbox="allow-scripts"`): no
  cookie, no storage, no access to the page around it, and no request leaves
  it — the page fetches the module without credentials, checks it against
  `integrity`, and hands it over. It is given its properties and what it
  shows, and what it sends is taken under a name of `sends` only.

### Messages that change

A message sent is not final:

```python
found = await session.send("Searching…")
rows = await run_sync(search, query)          # blocking code, in a thread
await found.update(f"Found {len(rows)}.")     # the same message, changed in place
note = await session.send("Read the first three.", author="Searcher")
await note.remove()                           # taken away from the conversation
```

- `await message.update(text)` — or `session.update(message, text)` —
  changes what it says where the person reads it, and returns the message
  as it is now: the same id, the same author. A streamed message changes the
  same way.
- `await message.remove()` — or `session.remove(message)` — takes it away.
  A removed message cannot be changed again (`ValueError`), and only the
  session that sent a message changes it.
- `author` names who wrote a message, the application's name unless said: the
  page draws a message by anybody else under that name, and the terminal
  prints it before the text.

On the channel, a message changed is the same `Message` delivered again
under its id; one removed is a `Removed(message_id, session_id)`.
`MemoryChannel.messages` says the conversation as it is now. Over the
[Session API](./session-api) a change is the message written again under its
id, and the author or the removal a `loop.message` event. A terminal does not
write over what it printed: it prints the message again, marked
*↻ edited*, or says *✗ a message was removed.*

### Small conveniences

Handlers are sync or async alike. Besides:

- `await run_sync(function, *args, **kwargs)` runs blocking code — a file
  read, `pandas`, a client without `async` — in a thread, so that the
  session's other work goes on. An async function is refused: await it.
- `@cache` keeps what a function answers for its arguments, for every session
  of the process. Sync or async; an async one called again while its first
  call runs waits for that call rather than running twice; what it raised is
  not kept; its arguments are hashable; `fn.cache_clear()` forgets.

```python
from agent_runtimes.loop.apps import cache, run_sync

@cache
async def prices(region: str) -> dict:
    return await fetch_prices(region)
```

### Steps

```python
async with session.step("Searching", kind="tool", input=query) as step:
    step.output = await search(query)
```

A step shows the person what the application is doing while it does it.
`kind` is `run` (the default), `tool`, `model` or `retrieval`. A step opened
inside another is nested in it. Each is delivered twice: when it starts, and
when it ends — with its output, or with the error that ended it.

Steps are the application's chain of thought:

- **In the conversation**, each is a row the chat draws as it draws a tool
  call — collapsed, running until it ends, its kind and input inside, then
  its output or its error; a nested step says the step it is in (*tool
  step, inside Researching*). Over the [Session API](./session-api) a step
  is AG-UI's `STEP_STARTED` and `STEP_FINISHED`, and beside each a
  `loop.step` event that says it whole.
- **In the record**, each step that ended is a `step` entry when the
  Appspec's `record.include` names `actions`: `{id, name, kind, parent_id,
  input, output, error, started_at, ended_at}`, its input, output and error
  cut and redacted as a tool call's are. They are sent when the outermost
  step ends.

### Asking

`await session.ask(question, timeout=None)` stops and asks the person, then
goes on with their answer:

| Question | The answer |
| --- | --- |
| a `str`, or `TextQuestion(prompt)` | Text. |
| `ChoiceQuestion(prompt, options)` | One of the options. |
| `FileQuestion(prompt, accept=(), max_bytes=20 MB)` | An `UploadedFile` (`name`, `media_type`, `content`); `accept` lists media types (`image/*`) or extensions (`.pdf`). |
| `FormQuestion(prompt, schema)` | A dict by field name. `schema` is the JSON Schema of a form, as the settings and a Form block say theirs (an object of named fields; anything else raises `ValueError`): the answer is checked against it, defaults filled in. |

An answer that does not answer the question raises `InvalidAnswer`, in a
sentence; no answer within `timeout` seconds raises `AskTimeout`.

### What a person sends

A person sends a file two ways: when the application asks
(`FileQuestion`, or a File upload block of its page), and **without being
asked**, attached in the composer to a message (LOOP P-21). What it takes
then is said in its Appspec — the kinds, each with its largest size, and how
many at once — and nothing else is sent:

```python
app = Application.from_spec({
    # …
    "interface": {
        "uploads": {
            "kinds": [
                {"type": "image/*", "max_mb": 5},
                {"type": "application/pdf"},
                {"type": ".csv", "max_mb": 2},
            ],
            "max_files": 3,
        },
    },
})

@app.file
async def received(session: Session, files: list[UploadedFile], text: str):
    names = ", ".join(file.name for file in files)
    await session.send(f"Thanks for {names}. {text}")
```

A kind is a media type, a family (`image/*`, `audio/*`) or an extension;
`max_mb` is 10 unless said, 25 at most; `max_files` 5 unless said. The
composer offers a paper clip that takes those kinds and refuses the rest in a
sentence before anything is read; the runtime refuses again, with 422 and the
same sentence, what a client sent around the page (*p.png is 6.0 MB: Photo
Desk takes image/* of at most 5 MB.*). Without `uploads` the composer offers
no attachment, and a file sent with a message is refused.

Without `@app.file`, the words go to `@app.message` (or its agent), and the
files wait for what the code asks next: `await
session.ask(FileQuestion(...))` is answered by one at once. An application
without code gives them to its agent: a text file in the message, an image, a
recording or a PDF whole to its model, anything else in its sandbox when its
permissions turn a shell on (see [Files](./session-api#files)).

### The record

`await session.record(payload, summary="", kind="output")` writes an entry
to the application's record and sends it at once. `kind` is `output`,
`tool_call`, `decision`, `check`, `approval`, `feedback`, `turn` or `step`. It
returns whether the application keeps entries of that kind: only those its
Appspec's `record.include` names (`outputs`, `actions`, `decisions`,
`checks`, `approvals`, `feedback`, `conversations`) are kept. A session's
start and what its channels were sent (`notification`, see *Its
notifications*) are kept whatever it names.

Each turn of a conversation that ends in an answer is kept by itself, as a
`turn` entry, when `record.include` names `conversations`: what the person
asked and what it answered — `{"asked", "answered", "suggest_tests"}`, each
text redacted as every entry is and cut at 4,000 characters. A run that was
stopped, or whose client went before the answer, keeps none. `suggest_tests`
is the Appspec's `record.suggest_tests` when the turn was had: whether the
application let its conversations be used to suggest tests to its builder.
Off unless said, and only a turn kept while it was on is ever sampled into a
suggested test.

### Threads and feedback

A session is a **thread** in the history of the person who had it: listed
newest first, found by its title or by what was asked, renamed and tagged
by that person (at the application's address, *Your conversations*). Its
code can name it too (LOOP P-24):

```python
@app.message
async def reply(session, text):
    if not session.title:
        session.title = f"Order {text[:40]}"
    session.tags = [*session.tags, "orders"]
    session.metadata["customer"] = "c-42"
    ...
```

- `session.title`: its title, at most 200 characters; `""` until said, and
  the person's first question stands for it then.
- `session.tags`: a tuple; set it whole. Each tag is said once, at most 40
  characters, at most 20 of them.
- `session.metadata`: a dict of names and JSON values, at most 10,000
  characters written. Every change is kept.

**Turns.** Each message a person sends is a turn of the thread — what they
asked and what was answered, kept when `record.include` names
`conversations` — whether the code's agent answered it or the code answered
by itself (`session.send` with no model): the history counts it, and finds
the thread by the words asked. A turn its agent answered is kept once.

Each change is a `thread` entry of the record, always kept and sent at once;
the latest one stands. The history lists the thread under the person's own
word over the code's: their title over its, its tags and theirs, their
metadata over its. A value too long or too many tags raises `ValueError`
and nothing changes.

**Feedback.** When `record.include` names `feedback`, a thumb up or down
and a comment are offered under each answer. What a person says is kept as
a `feedback` entry of the session — `{"liked", "comment", "message", "by"}`,
`message` naming the answer by its place in the conversation (`answer-2`) —
and then `@app.feedback(session, feedback)` runs; what it sends is kept in
the conversation. Feedback is kept on the conversation's application —
the one whose agent recorded it on that runtime, a deployment's kept always
on (whose agent runs the version's `app.py`) as much as a configured one; a
conversation the runtime did not record is refused (404, *This runtime runs
no application.* when it runs none). Its owner lists a thread's feedback
from the terminal:

```bash
loop apps threads <app> --search export --tag csv   # your threads, newest first, each with its id
loop apps feedback <session>                       # 👎 on answer-2 by bob: Too long.
```

A thread is opened again from the history: the chat reads its conversation
from the runtime that holds it (`GET /api/v1/apps/sessions/{uid}/messages`),
else resumes it from its record (`POST …/sessions/{uid}/resume`), and goes on
with it on the same thread (see the [Session API](./session-api)). A thread
whose application keeps no conversations cannot be resumed from its record.

### The agent

`session.agent` is the application's agent in this session (`AppAgent`),
with its rules, its checks and its record attached:

- `await session.agent.run(prompt, **context)` — the whole answer, an
  `Answer` with `text` and `output`. Keyword arguments are told to the agent
  for this turn (`goal="…"`).
- `session.agent.stream(prompt, **context)` — the answer's text, piece by
  piece.

Every run is a turn of the session's conversation: the history is kept from
turn to turn. A rule that says *ask first* asks the person of this session —
a `ChoiceQuestion` with *Allow* and *Refuse* — and a refusal raises
`AppRuleBlockedError`.

The host builds the agent. `local_agent`, the default, builds it in this
process from the Appspec: the application's model and instructions, else its
agent's, with the contexts it works under between its agent's prompt and its
instructions — `local_agent(app, read_organization_frames(...))` for its
organization's, the catalogue's otherwise. What only a runtime brings — connections, skills, tools, a team —
is refused with `AppNotRunnable` rather than left out, as is an application
that names no model. A host may pass its own `agent=` factory, as the
example does.

On a Datalayer runtime the agent's model is called through ai-inference,
naming the application and deployment it serves — and so is a model the
page's chat names on a request (its model picker, a hosted page's agent):
it is called as the agent's own model is, never directly. A runtime of your
own that calls Bedrock directly needs an AWS region (`AWS_REGION` or
`AWS_DEFAULT_REGION`); without one, a request naming a Bedrock model is
refused before anything is asked, saying so.

## An agent of your own: other frameworks

`app.agent(...)` gives the application an agent written in your code, in
place of its agent's (LOOP P-23): a plain function, a LangGraph graph or a
LangChain runnable, a LlamaIndex agent or workflow. `session.agent` is then
that agent, with the same `run` and `stream`, so an application with no
`@app.message` is answered by it, and code that calls `session.agent` does
not change. Wherever the application runs — `loop apps run`, a runtime, a
mount — its sessions get it: it is the application plugin's contribution to
`loop.app.agent`.

What it does becomes the session's **steps** (see [Steps](#steps)): a step
for the run, named after the agent, and nested in it a step per model call
and per tool call, with its input and its output — the chain of thought the
chat shows, kept in the record with the tool calls, the decisions, the
person's approvals and the turn.

The spec still names an agent of the catalogue (`agent=`): what answers where
the file does not run. `loop apps build` marks the agent of the code —
`# loop:code agent langgraph: research (app.py:12)` — and the Studio's Canvas
shows it, locked, as the rest of what the code decides.

Each framework is an extra, so that nothing is installed for an application
that does not use it:

```bash
pip install 'agent-runtimes[langgraph]'    # LangGraph, and LangChain's core
pip install 'agent-runtimes[langchain]'    # LangChain's core alone
pip install 'agent-runtimes[llamaindex]'   # LlamaIndex's core
```

An `app.py` importing a framework that is missing is refused in one sentence
naming its extra: *app.py does not load. It needs LangGraph, which is not
installed here: pip install 'agent-runtimes[langgraph]'.*

### A plain function

```python
@app.agent
async def answer(text: str, history: list) -> AsyncIterator[str]:
    yield "You said "
    yield text
```

Sync or async; returning the answer's text, or yielding its pieces, which are
streamed as they come. Blocking code runs in a thread. Besides the prompt it
is given, by name, what it asks for: `session`, `history` (the turns so far,
as `{"role", "content"}`), `instructions` (the modes' and profile's), and what
the code tells the agent for a turn — `session.agent.run(text, goal="…")`
gives `goal=` to a function that takes it, and is refused in a sentence by
one that does not.

### LangChain and LangGraph

```python
from langgraph.prebuilt import create_react_agent

graph = create_react_agent(model, [search, send_email])
app.agent(graph, name="research", tools={"search": "read", "send_email": "send"})
```

The graph runs with `astream_events`: its model's tokens are the answer, as
they come; each model call, tool call and retrieval is a step. A turn is
given as `{"messages": [...history, ("user", prompt)]}` — the history kept by
the session, or by the graph when it has a checkpointer (the session's id is
its `thread_id`) — what the code tells the agent for a turn said as a system
message before it. A LangChain runnable is given the prompt alone. Another
shape is said with `input=`:
`app.agent(chain, input=lambda prompt, **context: {"question": prompt})`.

**Its rules decide every tool it calls through LangChain's tools.** A
callback handler given to each run decides each call in `on_tool_start`,
before the tool runs: the rules, then the built-in checks and the Gates
(R-06), then the checks of its code (`@app.check("tool_call")`). A call the
rules ask about asks the person of the session; refused, the tool does not
run and the turn stops with `AppRuleBlockedError`, its sentence the rule's.

`tools=` says what each tool does — `read`, `write`, `send`, `buy`, `delete`,
`publish` — as `@app.tool(does=...)` does, and declares it in the spec, with
the description and parameters the framework gives it, so that the Canvas
lists it and a rule can name it. Every tool the graph is found to have (its
tool nodes; a runnable's `tools`) must be said, and a tool said that it does
not have is refused. A tool it finds as it runs and nobody said is left to
the person, and so refused.

### LlamaIndex

```python
from llama_index.core.agent.workflow import ReActAgent

agent = ReActAgent(tools=[search, send_email], llm=llm)
app.agent(agent, name="research", tools={"search": "read", "send_email": "send"})
```

A LlamaIndex agent (`FunctionAgent`, `ReActAgent`, an `AgentWorkflow`) runs
with `stream_events`; its memory is kept from turn to turn of the session. A
step per model call — what it wrote, its reasoning for a ReAct agent, as the
step's output — and per tool call. **Its answer comes whole when the run
ends**: what a LlamaIndex agent streams is its reasoning as well as its
answer.

**Its rules decide every tool the agent calls.** Given to the application,
the agent's tool calls are taken over: each is decided in its session, as a
LangChain tool's is, and a call made outside a session is refused. A
workflow of your own is run with `run(user_msg=prompt)` (or what `input=`
returns); each event it writes to its stream is a step, and its result the
answer.

### What the rules see, and what they do not

| The agent | Its tool calls |
|---|---|
| A LangGraph graph, a LangChain runnable | Decided, each one, before it runs |
| A LlamaIndex agent | Decided, each one, before it runs |
| A plain function, a LlamaIndex workflow | **Not seen**: no rule decides them |

LOOP does not see what a plain function or a workflow calls: `loop apps
validate` says so — *needs attention*: *Its agent is a plain function,
answer: LOOP sees none of the tools it may call, so its rules decide none of
them* — so that the verdict never passes for what the rules never saw.

What every agent of the code gets: a credential is withheld from its answer
as it streams; an answer that a Gate or a check of its code reads is given
whole once they let it through, and not at all when they refuse it — a
framework's model cannot be asked again, as a catalogue agent's is. What it
does not get: connections, skills, backend tools, documents to answer from,
a Space to save to and a team are tools LOOP gives an agent of the
catalogue; an application declaring them with an agent of its code is
refused, and so is `@app.tool` beside `app.agent`: give the tool to the agent
itself. The modes' and profile's instructions are told to it; their model is
not run — its model is its own.

## Mounted into your own FastAPI

An application runs inside a FastAPI of your own, under a path of its own
(LOOP P-25):

```python
from fastapi import FastAPI

from my_app import app  # an Application, its code attached

api = FastAPI()
app.mount(api, path="/assistant")
```

`uvicorn main:api` then serves, under `/assistant`:

- **its page**, at `/assistant`: the application, embedded with
  `<datalayer-app server="…/assistant">` and its Appspec written in the
  element (see [Embedding](./embedding));
- **the runtime's own routes**: the [Session API](./session-api) at
  `/assistant/api/v1/apps/sessions`, the chat's AG-UI at
  `/assistant/api/v1/apps/agents/<id>/ag-ui/`, and the rest of
  agent-runtimes' routes — the runtime is mounted as it is;
- **its agent**, made when your FastAPI starts, as the platform makes an
  application's (`POST /api/v1/agents` with its Appspec, in process): the
  runtime's lifespan runs inside yours;
- **its code**: `@app.message`, `@app.file`, `@app.window` and the rest react
  to its sessions, as the catalogue's Python examples do on a runtime.

| Parameter | What it says |
| --- | --- |
| `path` | Where it is served: `/assistant` unless said. A path of its own: not `/`, no trailing slash. |
| `app_uid` | The application as Datalayer knows it, when an embed token names it. |
| `token` | `token(request)` gives the page the visit's embed token, issued by your server for each visit ([Private applications](./embedding#private-applications)); none for a page only the machine itself opens. |
| `embed_origin` | Where the embed's script is served: `https://datalayer.ai` unless said. |
| `config` | The runtime's `ServerConfig`; its defaults unless said. |

Who may call is decided as on any runtime: the machine itself needs no
token; anybody else sends a person's token or an embed token, from an origin
the Appspec names (`deployment.embedded.origins`) — your page's own included.
Your own routes stay yours: the mount answers its path and nothing else.

### Window messages

The application and the page it sits in talk outside the conversation:

```python
@app.window
async def from_page(session: Session, data: dict):
    if data.get("page") == "/checkout":
        await session.send_window_message({"highlight": "coupon"})
```

```js
const element = document.querySelector('datalayer-app');
element.addEventListener('window-message', event => {
  console.log('the application says', event.detail.data);
});
await element.postWindowMessage({ page: location.pathname });
```

`await session.send_window_message(data)` — anything JSON writes — is raised
on the element as its `window-message` event, whether its code sends it in
a turn of the conversation or in answer to the page. The page posts with
`element.postWindowMessage(data)`, on the application's own server (the
`server` attribute), once its conversation has started: its `@app.window`
runs on it, and a session whose code has none refuses it in a sentence. A
window message is not a message of the conversation: the person does not see
it, and it is no turn of theirs. Beside them, the host's values and
functions (`host_context`, `host_<name>`) are what its agent reads and
calls, each decided by its rules ([The page and the application,
talking](./embedding#the-page-and-the-application-talking)).

## Channels

A session talks to the person through a `Channel`: anything with two
methods.

```python
class Channel(Protocol):
    async def deliver(self, event: Message | Delta | Step) -> None: ...
    async def ask(self, session_id: str, question: Question) -> Any: ...
```

A channel that cannot ask raises with a sentence; it never answers for the
person.

`MemoryChannel` is the one in this process, for tests and for whoever
drives an application from Python: `events` holds everything delivered, in
order; `messages` the whole messages; `questions` everything asked; and
`reply(answer)` answers the question being asked, or the next one.

## From the command line

`loop apps init` starts one: a folder named by its id, with an `app.py`, the
spec it builds and `tests/test_app.py` — its CI's checks, the build among
them — blank or from an example of the catalogue:

```bash
loop apps init my-app --python
loop apps init interview --from customer-interview
```

See [A new application](/cli#a-new-application) for every option.

`loop apps build` writes the Appspec an `app.py` amounts to — its
`Application.spec`, as YAML — printed, or to a file with `--out`
(`--force` to overwrite):

```bash
loop apps build app.py
loop apps build app.py --out app.yaml
```

What the code decides is marked as code at the top of the spec, in comments,
one line per handler, with where it is:

```yaml
# Built from app.py by `loop apps build`: the file is the source; edit it there.
# What its code decides; without the file, its agent answers:
# loop:code start: opening (app.py:7)
# loop:code message: reply (app.py:12)
schema: loop.app/v1
id: echo-desk
...
```

An Appspec refuses fields it does not define, so the marks are comments: the
built file validates, is pushed and is deployed as any Appspec is. The build
is refused, with a sentence and exit code 1, when the file does not load,
defines no `Application` or more than one, or its spec does not validate (the
reasons of `AppNotRunnable`).

`loop apps validate`, `loop apps run` and `loop apps push` take an `app.py`
as they take a spec: they build it first. `deploy` deploys a saved version
by its id, so a Python application reaches it through `push`.

**Where the file lives.** `loop apps push app.py --app <id>` keeps the file
itself in the application's item, beside the spec it builds — `code`,
`{"file": "app.py", "text": …}` in the item's content — and versions it with
the spec: a changed file is the next version, even when the spec it builds
is the same, and the version left behind keeps its own file. `loop apps pull
<id>` writes it back, `app.py` beside `app.yaml` (neither overwritten without
`--force`). An application kept with its file is refused a spec pushed
without it (*… is written in Python: push its app.py, which builds this
spec.*). The Studio shows the file in the application's **Python** tab, every
line numbered, and the Canvas links each thing the code decides
(`app.py line 23`) to its line there. An application of several files keeps
its `app.py` only.

**Changed in the Studio.** The Python tab is an editor too. *Run in a
sandbox* sends the file to a runtime of the person's on Datalayer —
`POST /api/v1/apps/build` with `{"file": "app.py", "text": …}` — which builds
it in a Python process of its own, for at most a minute, and answers the
Appspec it builds, what its code decides marked at the top (`{"spec": …}`),
or, 422, why it does not build (`{"detail": {"problems": [...]}}`): a file
that never ends is stopped, not the runtime's server. The Studio takes the
file and that spec as its draft, saved as any change is — a changed file is
the next version once the one it was at has run or shipped. Nothing is kept
on the runtime. The route answers a person, never a visitor or an embed.

**From a spec.** An application built by spec or on the Canvas becomes one
written in Python with `loop apps eject app.yaml`: an `app.py` holding its
spec, ready for code, which builds it the same. One way, said before it is
done; see the [CLI](../cli#eject-an-application-into-python). The Studio's
Python tab has the same *Eject*: `POST /api/v1/apps/eject` with `{"spec": …}`
answers the `app.py` and the spec it builds — checked to be the same, else
refused with why — and the Studio saves both as the application's next
version, the ones before it kept. The `SPEC` an ejected `app.py` holds says no
`version`: the Studio numbers each version as it saves it, and the deployed
version is the one the code runs as (see *Its version* under `Application`).
Write a `version` into it only to pin the file to one version.

`loop apps run app.py` runs it as it runs a spec — a runtime here
(`--local`) or on Datalayer (`--cloud`), configured with the built Appspec,
in the terminal's renderer, the starters as its suggestions — and the
terminal is also the application's `AppHost`:

- **In this process**, through a channel to the terminal: `start` when the
  session opens, `message` when the application has one, an action with
  `/action <name> [json]`, its page with `/page [json]` (its outputs said),
  `end` when the person leaves; `session.ask` asks
  at the prompt. With a `message`, `--ask "…"` runs `start`, then it, once.
- **On the runtime**: a message the code does not take, answered by the
  runtime's agent with the application's rules, as for a spec.
- **Not from the terminal**: `settings` and `resume` from the person, and
  schedules, have no way in from the terminal; and `session.agent` in the
  code is built in this process, so an application whose agent needs
  connections, skills or tools is refused there (see [The agent](#the-agent)).
  On a runtime, the [Session API](./session-api) carries all three, and
  `session.agent` is the agent the runtime made, with its tools.

`--watch` builds the file again when it has changed, before the next turn:
the runtime is configured with the new spec, and the session goes on with
its state through the new code (`AppHost.resume`). A file that no longer
builds is said, and the application as it was goes on. For a spec,
`--watch` reconfigures the runtime the same way.
