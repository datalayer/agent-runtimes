# Chat

The React chat components in `@datalayer/agent-runtimes` — the conversation,
the composer, and everything around them. The [Loop Web](/loop) workspace
assembles these into a full workspace; this page is the components
themselves, for a host embedding a chat of its own.

![Agent Runtimes](https://images.datalayer.io/product/agent-runtimes/agent-runtimes-example-1.gif)

## ChatBase

The transcript-and-composer core. It owns the conversation: streaming
responses, tool-call rows with approval flows, the message list as a centred
reading column, and the empty state that introduces the agent with its
spec's own suggestions. Around it:

- **`ChatSidebar`** and **`ChatFloating`** wrap the same core for a side
  panel or a floating window.
- **`notebookToolSurfacesId`** — name a notebook document and notebook tool
  results render inline in the transcript: a cell that was inserted, updated
  or run appears under its tool row as a captioned surface — the change
  first (the cell source, read-only), then its outputs bound to the live
  model's output area, so a run that prints as it goes streams into the
  transcript. `executeCodeInNotebook` shows only its outputs. A host passing its own
  `renderToolResult` overrides this outright.
- **`onSendReady`** hands the host imperative controls — `send`, `stop`,
  `newChat` — for a page whose input lives outside the component (the Loop
  workspace's prompt does).

## InputPrompt

The composer, one component in every placement. It wraps the editor and adds
the rows around it:

- **The editor** (`InputPromptBase`): a plain textarea variant, or the
  **lexical** variant where `/` opens the command menu and `@` mentions
  agents, with typing suggestions cycling in the placeholder.
- **The session-controls footer**: the agents, tools, skills and model
  menus — each drawn when asked for, opening onto an honest count of zero
  rather than disappearing when empty — plus `footerExtras`, a trailing-edge
  opening for the host's own controls (the Loop's **+** — start the
  conversation over — arrives that way).

  The model menu lists what the agent runtime answers, and nothing else:
  for an agent, its agentspec's `model` and `model_additionals`, those its
  inference can run (`GET /api/v1/configure?agent_id=…`, `models`, each with
  `isAvailable` and why not). Routed through datalayer-ai-inference, the
  runtime asks the service which models it serves once, when it starts;
  `modelsSource` says who decided (`ai-inference`, or `local` when the
  runtime calls the providers itself or the service did not answer) and
  `modelsNote` says it in a sentence. A request naming a model the agent
  does not offer, or the service does not serve, is refused with a 400 and
  that sentence. Only an in-page agent, with no runtime to ask, offers the
  catalogue's available chat models instead.

  Under the models, the menu shows a **Judgments** group, read-only: the
  typed-judgment models ai-inference serves, such as Jev on Workers AI
  (`cloudflare:wrk/typesafe/jev`, named as the agentspecs catalogue names it,
  *Jev (Cloudflare Workers AI)*). The runtime answers them apart, in
  `judgmentModels` with `judgmentsNote` (`judgment_models` and
  `judgments_note` on `/api/v1/configure/models`), never among `models`, so
  no row of the group can be picked as the agent's model. Each row says what
  it is for: it answers a decision's typed questions, and agents do not chat
  with it; when it cannot be used, it says why first, as the models above do
  (`No ai-inference token` on a runtime waiting for its token). A decision
  asks it through ai-inference's `/judgments`, which this does not change. A
  request naming it as the agent's model is refused with a 400: `… answers
  typed judgments, not a conversation: an agent cannot run on it …`.
- **The context band**: `ContextPie` and the token counts, shown as soon as
  the agent accounts for itself.
- **`draggable`** wraps the whole prompt in `FloatingCard`: an absolutely
  positioned, draggable card — the same composer, floating over a canvas
  instead of docked under it.

### Prompt regions

Four regions surround the input, each a *list* of bands rather than a single
slot — see `chat/prompt/stack`:

| | above the input | below the input |
| --- | --- | --- |
| inside the box | `InPromptHeader` | `InPromptFooter` |
| under the box | `BelowPromptHeader` | `BelowPromptFooter` |

A band can reserve height for late-arriving content, draw as a flex row of
controls or as a self-painting block, and disappear entirely when empty.

## The empty state

`ChatEmptyState` introduces the agent — icon, name, description, and its
spec's suggestions as clickable chips — centred at the top of the canvas,
where the first message will appear beneath it.

## Display modes

`ChatFloating` shows a chat in five ways, offered by the toggle in its
header: *Full-height popup*, *Floating popup*, *Floating draggable*,
*Floating assistant* — a character on the page that speaks in a balloon —
and *Sidebar panel*, when the page gives it a place to dock. See [The
floating assistant](./floating-assistant.mdx) for the modes, the character,
its balloon, and the floating popup that blinks and speaks on hover.

## An application's presence

An application's chat shows its face, its name and its welcome, and one
line saying what it is doing — *Ready*, *Thinking…*, *Working…*, *Waiting
for you* — with a quiet ring around the face. See [An application's
presence](./presence.mdx), and `ChatPresence` and `onPresence` for a host.

## Where the pieces meet Loop

In the Loop workspace, all of this is assembled by the chat *plugin*: the
composer's placement (`bottom`, `bottom-chat`, `floating`) is plugin
configuration, the agent's tools arrive through the `LoopFrontendTool`
extension point, and the editors beside the conversation are contributions
the shell hosts. See [Loop Web](/loop).
