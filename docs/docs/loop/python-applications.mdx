# Applications in Python

An application can be written in Python, for logic no block covers. The API
lives in `agent_runtimes.loop.apps`, in agent-runtimes itself — no other
package to install. It uses the words of the Appspec: an *application*, its
*rules*, its *settings*, a *session*.

Three pieces:

- **`Application`** — the application: what it declares (its Appspec) and
  the code that reacts to its sessions.
- **`AppHost`** — what runs it in this process: it opens sessions and tells
  the application what the person does.
- **`Session`** — one conversation of one person with the application,
  handed to its code: to write, stream, show steps, ask, keep state, record,
  and call the application's agent. What the person sees goes through a
  **`Channel`**.

## What runs today, and what waits

Everything on this page runs **in process**, today: an application is
declared, a host opens its sessions and drives them, and its agent answers
with its rules, checks and record on. It is tested (see the end of the
page).

What does **not** exist yet:

- **A Python application of your own on a runtime.** A runtime runs the
  code of the catalogue's Python examples through the
  [Session API](./session-api) — its channel the session, what it shows
  streamed as AG-UI events, what it asks answered from the page — and an
  `app.py` saved elsewhere runs as the spec it builds, answered by its agent.
- **`loop apps init`**, which scaffolds an `app.py` from an example.
  `loop apps build` and `loop apps run app.py` exist: see
  [From the command line](#from-the-command-line).
- **An agent with tools in process.** An application whose agent needs
  connections to MCP servers, skills, tools or a team runs on a runtime;
  built in this process, it is refused with the reason (see
  [The agent](#the-agent)).
- **Tests and checks in code** (`@app.test`, `@app.check`, `@app.tool`) and
  what an answer shows beyond text (tables, charts, buttons).

## A runnable example

A customer interview: it asks the person what they want to learn when the
session starts, answers each message through its agent inside a step, and
saves an insight from a button. The person is played by a `MemoryChannel`,
and the agent by pydantic-ai's `TestModel`, so the script runs with no key
and no network:

```python title="interview.py"
import asyncio

from pydantic_ai import Agent
from pydantic_ai.models.test import TestModel

from agent_runtimes.loop.apps import (
    AppHost,
    Application,
    ChoiceQuestion,
    MemoryChannel,
    Session,
)
from agent_runtimes.loop.apps.record import AppRecorder

# The application: what it declares is its Appspec.
app = Application(id="customer-interview", kind="chat", agent="cog-crawler:0.0.1")
app.starter("Onboarding", "Interview me about my onboarding.")
app.rule("send the summary by email", applies_to="send", behaviour="ask_first")
app.setting("tone", "select", "Tone", options=["warm", "dry"], default="warm")
app.setting("depth", "slider", "Depth", default=3, min=1, max=5)


# What it reacts to.
@app.start
async def opening(session: Session) -> None:
    session.state["goal"] = await session.ask("What do you want to learn?")


@app.message
async def reply(session: Session, text: str) -> None:
    async with session.step("Thinking", kind="model", input=text) as step:
        answer = await session.agent.run(text, goal=session.state["goal"])
        step.output = answer.text
    await session.send(answer.text)


@app.action("save")
async def save(session: Session, payload: dict) -> None:
    session.state["kept"] = await session.record(payload, summary="An insight")
    keep = await session.ask(ChoiceQuestion("Keep interviewing?", ("Yes", "No")))
    session.state["done"] = keep == "No"


async def main() -> None:
    channel = MemoryChannel()
    sent: list = []

    async def send(body: dict) -> None:  # the record, kept here and not sent
        sent.append(body)

    host = AppHost(
        app,
        channel,
        # A model that answers without being called: no key, no network.
        agent=lambda spec: Agent(TestModel(custom_output_text="Tell me about week one.")),
        recorder=AppRecorder(app=app.spec, send=send),
    )

    channel.reply("why people leave")            # the answer to `start`'s question
    session = await host.open(user="ada", settings={"depth": 4})
    print(session.state, session.settings)

    await host.message(session, "Hello")
    print(channel.messages[-1].author, "-", channel.messages[-1].text)

    await host.settings(session, {"tone": "dry"})
    channel.reply("No")
    await host.action(session, "save", {"insight": "pricing is unclear"})
    print(session.state)
    print([type(q).__name__ for q in channel.questions])


asyncio.run(main())
```

```text
$ python interview.py
{'goal': 'why people leave'} {'tone': 'warm', 'depth': 4}
Customer interview - Tell me about week one.
{'goal': 'why people leave', 'kept': False, 'done': True}
['TextQuestion', 'ChoiceQuestion']
```

`kept` is `False`: the application keeps no outputs in its record unless its
Appspec's `record.include` names them (see [The record](#the-record)).

The scenario is the one `agent_runtimes/tests/test_loop_app_api.py` runs
(`interview()`, `hosted()`), where the model is scripted turn by turn.

## `Application`

```python
from agent_runtimes.loop.apps import Application

app = Application(
    id="customer-interview",
    kind="chat",                       # chat, widget, decision or worker
    agent="cog-crawler:0.0.1",         # or team="…"
    name="Customer interview",         # its id in words when unsaid
    description="Interviews a customer about their onboarding.",
    instructions="Never ask a leading question.",
    model="",                          # in place of its agent's model
    goal="",                           # for a worker
    version="0.0.1",
)
```

Or attach code to an Appspec that already exists — read from its YAML, or as
an `AppSpec`:

```python
app = Application.from_spec(spec)
```

### Declarations: plain calls

What an application declares is its Appspec. Each call adds to it:

| Call | Declares |
| --- | --- |
| `app.starter(label, message)` | A first message offered to the person. |
| `app.setting(id, type, label, *, options=(), default=None, min=None, max=None)` | A setting of the session: `select`, `text`, `toggle`, `slider` or `number`. |
| `app.rule(action, *, applies_to, behaviour)` | When it acts alone and when it asks: `applies_to` names classes of action (`send`, `write`…) or tools (`server.tool`); `behaviour` is `do_it`, `if_asked`, `ask_first` or `leave_to_me`. |
| `app.connection(server, *, access="read", acts_as="owner", only=())` | An MCP server it reaches, read or write, in the owner's or the person's name, limited to the tools `only` names. |

`app.spec` is the Appspec they amount to, **validated** as any Appspec is:
an application that would not run raises `AppNotRunnable` with its reasons,
in sentences. `app.document` is the same as a plain dict, as its YAML would
say it.

### Reactions: decorators

What an application reacts to, one handler per moment — sync or async, the
session always first:

| Decorator | Called with | When |
| --- | --- | --- |
| `@app.start` | `(session)` | A session starts. |
| `@app.message` | `(session, text)` | The person writes. Without a handler, the application's agent answers, streamed. |
| `@app.action(name)` | `(session, payload)` | The person presses the button of that name. |
| `@app.settings` | `(session, settings)` | The person changes settings; given all of them, checked. |
| `@app.stop` | `(session)` | The person presses Stop, after what was running is cancelled. |
| `@app.resume` | `(session)` | An earlier session is reopened, its state back. |
| `@app.schedule(cron, *, description="", prompt="")` | `(session)` | On a schedule, in a session of its own. Also adds the schedule to the Appspec's triggers. |

A second handler for the same moment, action or schedule raises
`ValueError`.

### Schedules on the platform

A deployed application's schedules fire with nobody at a browser. When an
application is deployed, each `schedule` trigger of the deployed version is
registered with the platform's scheduler; on each tick the scheduler
launches a runtime, creates the application's agent on it as the hosted
page does, asks it the trigger's `prompt` (its `description` when it has no
prompt), and stops the runtime. Pausing the deployment stops its schedules,
resuming starts them again, taking it down removes them; deploying another
version registers that version's schedules. Every tick is a run of the
schedule, which says whether it answered.

What runs on the platform is the Appspec: the code of a `@app.schedule`
handler runs where an `AppHost` runs it (`host.schedule(name)`), not on the
platform's tick. A schedule with neither a prompt nor a description is
refused at deploy: a session woken with nothing to ask does nothing. An
application run by a team is not woken yet.

The record of a session nobody opened says what woke it: `woken_by`,
`{"kind": "schedule", ...}` — the schedule, its cron, and on the platform
the scheduler's run — sent with its entries and written on its first.

### In whose name it acts on the platform

A deployed application acts as itself: its **service principal**, made at
its first deploy, with a token narrowed to what the version it runs was
granted — never with the token of the person who launched the runtime.

- **What it may reach** is read from the deployed version's Appspec — each
  connection (its server, `read` or `write`, in whose name, its `only`), each
  Space, and the parts of its computer turned on — and kept by the platform
  as the deployment's grant (RFC 9396 `authorization_details`). An
  application granted nothing has an empty list, and reaches nothing.
- **Its token.** The agent of a deployment is created on a runtime with
  `app_instance.deployment_uid` and the token of whoever opens its session
  (the hosted page, the scheduler's tick). The runtime asks ai-agents for the
  principal's token with it (`POST /api/ai-agents/v1/apps/deployments/{uid}/principal-token`)
  before the agent is made, keeps it in memory by deployment
  (`agent_runtimes.loop.apps.principal`), and asks again, with the latest
  request's token, when less than five minutes of its hour are left.
- **What it is used for**: the agent's model calls through ai-inference
  (metered on the application's owner, naming the deployment and the
  principal), the Datalayer MCP gateway, and the session's record. The
  runtime's inference token and `DATALAYER_USER_TOKEN` are never used in its
  place.
- **Fail fast.** Without the token the agent is not created (422, in a
  sentence); once it has expired the agent calls nothing and says so, and a
  chat request is answered 403.
- **Withdrawn, at once.** Every service reading the token asks whether its
  grant still stands, and remembers the answer ten seconds. Moving the
  deployment to a version granting less, pausing it, taking it down or
  deleting the application revokes the grant, so the token stops being
  honoured within ten seconds, not at its expiry.

A Preview, a test run and an agent no application runs keep the runtime's
own inference token: they are a person trying something, not a deployment
acting alone.

## `AppHost`

`AppHost(app, channel, *, agent=local_agent, recorder=None)` runs an
application in this process. A runtime, a test or a script drives it:

| Method | Does |
| --- | --- |
| `await host.open(user=None, settings=None)` | Opens a session and runs `start`. Returns the `Session`. |
| `await host.message(session, text)` | Runs `message`, or lets the agent answer. |
| `await host.action(session, name, payload=None)` | Runs the action; an unknown one raises `KeyError`. |
| `await host.settings(session, values)` | Checks the values, keeps them, runs `settings`. A value its input does not take raises `InvalidAnswer`. |
| `await host.stop(session)` | Cancels what runs in the session, then runs `stop`. |
| `await host.resume(session_id, state, user=None, settings=None)` | Reopens a session with its state, and runs `resume`. |
| `await host.schedule(name)` | Runs a schedule now, in a new session whose record says the schedule woke it. |

Each handler runs as one turn: it can be stopped, and the record of the turn
is sent when it ends. `agent` says how the application's agent is built
(`local_agent` unless said); `recorder` where its record goes (to the
platform unless said).

`load_application(path)` returns the one `Application` an `app.py` defines;
a file with none, or more than one, raises `ValueError`.

## `Session`

A session is made by the host and handed to the application's code — never
made by that code.

| | |
| --- | --- |
| `session.id` | The session's id: its conversation and its record. |
| `session.user` | Who the person is, when the host knows. |
| `session.state` | A dict the application keeps across the turns of this session; each session has its own. |
| `session.settings` | The person's settings, by id, their defaults filled in; a copy. |
| `session.app` | The application, as its Appspec says it. |

### Writing to the person

- `await session.send(text, author=None)` — a message, by the application's
  name unless said. Returns the `Message`.
- `await session.stream(tokens, author=None)` — a message as it comes,
  piece by piece, from any iterable or async iterable of strings; each piece
  is delivered as a `Delta`, then the whole `Message`.
  `await session.stream(session.agent.stream(text))` shows the agent's
  answer as the model writes it.

### Steps

```python
async with session.step("Searching", kind="tool", input=query) as step:
    step.output = await search(query)
```

A step shows the person what the application is doing while it does it.
`kind` is `run` (the default), `tool`, `model` or `retrieval`. A step opened
inside another is nested in it. Each is delivered twice: when it starts, and
when it ends — with its output, or with the error that ended it.

### Asking

`await session.ask(question, timeout=None)` stops and asks the person, then
goes on with their answer:

| Question | The answer |
| --- | --- |
| a `str`, or `TextQuestion(prompt)` | Text. |
| `ChoiceQuestion(prompt, options)` | One of the options. |
| `FileQuestion(prompt, accept=(), max_bytes=20 MB)` | An `UploadedFile` (`name`, `media_type`, `content`); `accept` lists media types (`image/*`) or extensions (`.pdf`). |
| `FormQuestion(prompt, fields)` | A dict by field id. The fields are settings (`AppSettingSpec`): the same inputs, checked the same way, defaults filled in. |

An answer that does not answer the question raises `InvalidAnswer`, in a
sentence; no answer within `timeout` seconds raises `AskTimeout`.

### The record

`await session.record(payload, summary="", kind="output")` writes an entry
to the application's record and sends it at once. `kind` is `output`,
`tool_call`, `decision`, `check`, `approval`, `feedback` or `turn`. It
returns whether the application keeps entries of that kind: only those its
Appspec's `record.include` names (`outputs`, `actions`, `decisions`,
`checks`, `approvals`, `feedback`, `conversations`) are kept.

Each turn of a conversation that ends in an answer is kept by itself, as a
`turn` entry, when `record.include` names `conversations`: what the person
asked and what it answered — `{"asked", "answered", "suggest_tests"}`, each
text redacted as every entry is and cut at 4,000 characters. A run that was
stopped, or whose client went before the answer, keeps none. `suggest_tests`
is the Appspec's `record.suggest_tests` when the turn was had: whether the
application let its conversations be used to suggest tests to its builder.
Off unless said, and only a turn kept while it was on is ever sampled into a
suggested test.

### The agent

`session.agent` is the application's agent in this session (`AppAgent`),
with its rules, its checks and its record attached:

- `await session.agent.run(prompt, **context)` — the whole answer, an
  `Answer` with `text` and `output`. Keyword arguments are told to the agent
  for this turn (`goal="…"`).
- `session.agent.stream(prompt, **context)` — the answer's text, piece by
  piece.

Every run is a turn of the session's conversation: the history is kept from
turn to turn. A rule that says *ask first* asks the person of this session —
a `ChoiceQuestion` with *Allow* and *Refuse* — and a refusal raises
`AppRuleBlockedError`.

The host builds the agent. `local_agent`, the default, builds it in this
process from the Appspec: the application's model and instructions, else its
agent's. What only a runtime brings — connections, skills, tools, a team —
is refused with `AppNotRunnable` rather than left out, as is an application
that names no model. A host may pass its own `agent=` factory, as the
example does.

## Channels

A session talks to the person through a `Channel`: anything with two
methods.

```python
class Channel(Protocol):
    async def deliver(self, event: Message | Delta | Step) -> None: ...
    async def ask(self, session_id: str, question: Question) -> Any: ...
```

A channel that cannot ask raises with a sentence; it never answers for the
person.

`MemoryChannel` is the one in this process, for tests and for whoever
drives an application from Python: `events` holds everything delivered, in
order; `messages` the whole messages; `questions` everything asked; and
`reply(answer)` answers the question being asked, or the next one.

## From the command line

`loop apps build` writes the Appspec an `app.py` amounts to — its
`Application.spec`, as YAML — printed, or to a file with `--out`
(`--force` to overwrite):

```bash
loop apps build app.py
loop apps build app.py --out app.yaml
```

What the code decides is marked as code at the top of the spec, in comments,
one line per handler, with where it is:

```yaml
# Built from app.py by `loop apps build`: the file is the source; edit it there.
# What its code decides; without the file, its agent answers:
# loop:code start: opening (app.py:7)
# loop:code message: reply (app.py:12)
schema: loop.app/v1
id: echo-desk
...
```

An Appspec refuses fields it does not define, so the marks are comments: the
built file validates, is pushed and is deployed as any Appspec is. The build
is refused, with a sentence and exit code 1, when the file does not load,
defines no `Application` or more than one, or its spec does not validate (the
reasons of `AppNotRunnable`).

`loop apps validate`, `loop apps run` and `loop apps push` take an `app.py`
as they take a spec: they build it first. `deploy` deploys a saved version
by its id, so a Python application reaches it through `push`.

`loop apps run app.py` runs it as it runs a spec — a runtime here
(`--local`) or on Datalayer (`--cloud`), configured with the built Appspec,
in the terminal's renderer, the starters as its suggestions — and the
terminal is also the application's `AppHost`:

- **In this process**, through a channel to the terminal: `start` when the
  session opens, `message` when the application has one, an action with
  `/action <name> [json]`, `stop` when the person leaves; `session.ask` asks
  at the prompt. With a `message`, `--ask "…"` runs `start`, then it, once.
- **On the runtime**: a message the code does not take, answered by the
  runtime's agent with the application's rules, as for a spec.
- **Not from the terminal**: `settings` and `resume` from the person, and
  schedules, have no way in from the terminal; and `session.agent` in the
  code is built in this process, so an application whose agent needs
  connections, skills or tools is refused there (see [The agent](#the-agent)).
  On a runtime, the [Session API](./session-api) carries all three, and
  `session.agent` is the agent the runtime made, with its tools.

`--watch` builds the file again when it has changed, before the next turn:
the runtime is configured with the new spec, and the session goes on with
its state through the new code (`AppHost.resume`). A file that no longer
builds is said, and the application as it was goes on. For a spec,
`--watch` reconfigures the runtime the same way.

## What is verified, and what is not

**Verified.** `agent_runtimes/tests/test_loop_app_api.py` runs every call on
this page in process: declarations becoming a validated Appspec, attaching
to an existing one, one handler per moment; start, message, action,
settings, stop, resume and schedule through an `AppHost`; the agent
answering, streamed, when there is no message handler; `send`, `stream`,
nested steps and their errors; `ask` with text, choice, file and form, wrong
answers and timeouts; state per session; the record; the agent's history
across turns; a rule asking the person and a refusal raising; the local
agent refusing what only a runtime brings; `load_application`. The example
above was run as printed. `agent_runtimes/tests/test_apps_build.py` covers
`build`, its refusals and its marks, `validate` and `push` of an `app.py`,
`run` serving one, the terminal routing to the code, and `--watch` rebuilding
with the session's state kept; `loop apps run app.py --local --ask` was run
against a local server.

**Not verified.** A Python application reached from a browser on a cloud
runtime: the [Session API](./session-api) runs one in process in its tests
(`test_app_sessions.py`, *Report from a File* taking its file from the page),
not yet live. The agent is scripted in the tests; no test calls a real model
through this API.

**Not built yet.** See [What runs today, and what waits](#what-runs-today-and-what-waits).
