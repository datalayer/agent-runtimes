# Session API

An application's sessions over the wire: **start**, **message**, **action**,
**settings change**, **stop** and **resume**, each streamed as the
[AG-UI](https://docs.ag-ui.com) events a chat already reads. It is how a page
— the Studio's Preview, the hosted page, an embed — and any other client drive
an application that runs on a runtime.

A session is one conversation of one caller with one application. Its **uid**
is also its AG-UI thread and the session its record is kept under in
ai-agents, so what the page shows, what the runtime ran and what the record
says are one thing.

The routes live in `agent_runtimes/routes/apps.py`, beside `configure`,
`decide` and `feedback`; what they drive is `agent_runtimes.loop.apps.sessions`.

## The application's agent first

A session is opened on the agent the platform made for the application, as it
makes one today: `POST /api/v1/agents` with the Appspec (`app_spec`) and the
instance it runs (`app_instance`: `app_uid`, `deployment_uid`, `version`).
The session API does not make agents; it refuses, in a sentence, an agent that
is not there or runs no application.

## In whose name it runs

- **A deployment's session** runs as its application's **principal**: the
  agent holds the principal's token, asked of ai-agents with the caller's
  token, and asked again with the latest request's token when it runs out
  (see *In whose name it acts on the platform* in
  [Applications in Python](./python-applications)).
- **A Preview's session** runs as the **person**: the agent was made without a
  deployment, on the runtime's own token.

A start names what it expects — a deployment, or none for a Preview — and is
refused when the agent runs something else: a Preview is never run by a
deployment's agent, and a deployment's session never by a Preview's.

Every route checks who is calling before anything else, as every application
route does: a person's token, an embed token for the application, nobody for a
public one, or the machine itself. A session answers only the caller who
opened it (and the machine itself); somebody else's is *not found*.

## Who may open a deployment

A hosted deployment says who may open it — only its owner, the people they
invite, their organization, anyone with the link, everyone — and ai-agents
decides. Before a session of a deployment is opened, and on each request of
one, the runtime asks ai-agents with the caller's own token
(`GET /api/ai-agents/v1/apps/deployments/{uid}/opens`) and refuses whoever it
does not let in, in its sentence (`403`, or `404` for a deployment only its
owner opens): the principal's token the runtime already holds for the
deployment is no reason to let anybody else talk to it. An answer is kept a
minute per deployment and caller. A caller with no token holds no session of a
deployment, whatever its level (`401`, *needs a Datalayer account*):
conversations without an account are not built yet. A visitor let in acts, as
the owner does, through the application's principal, whose token ai-agents
gets them from IAM.

## The routes

All under `/api/v1/apps`. Every route that runs something answers
`text/event-stream`: first a `CUSTOM` event named `loop.session` — the session
as `GET` says it — then the turn's events.

| Route | What it does |
| --- | --- |
| `POST /sessions` | **Start**: `{agent, deployment_uid?, app_uid?, version?, opener?, settings?, session?, woken_by?}`. The record begins (`woken_by` when nobody opened it), a Python application's `start` runs, then the opener is answered. |
| `POST /sessions/{uid}/messages` | **Message**: `{text}`. The next turn — or the answer to what the application asked. |
| `POST /sessions/{uid}/actions` | **Action**: `{name, payload?, text?, files?}`. A page block's action — File upload's `upload`, a Form's `submit`, a Table's `select` — with the files given. |
| `PUT /sessions/{uid}/settings` | **Settings change**: `{values}`, checked against the application's settings (`Tone is one of Plain, Warm.`) and kept. |
| `POST /sessions/{uid}/stop` | **Stop**: what runs is cancelled, a Python application's `stop` runs, the session waits to be resumed. Answers the session, as JSON. |
| `POST /sessions/{uid}/resume` | **Resume** a stopped session; or, with `{agent}`, one this runtime no longer holds, from its record. |
| `GET /sessions/{uid}` | What the session is. |
| `GET /sessions` | The caller's sessions on this runtime (`?agent=`). |
| `POST /agents/{agent}/ag-ui/` | The application's agent over **AG-UI**, each thread a session, opened at its first run. |

What `GET` says of a session:

```json
{
  "uid": "session-0001",
  "agent": "notes-assistant",
  "app": {"id": "notes-assistant", "version": "0.0.1", "name": "Notes Assistant", "kind": "chat"},
  "instance": {"app_uid": "app-1", "deployment_uid": "", "version": 3},
  "preview": true,
  "acts_as": {"kind": "person", "uid": "ada"},
  "opened_by": {"kind": "person", "uid": "ada"},
  "state": "open",
  "settings": {"tone": "Plain"},
  "asking": null,
  "files": [],
  "python": false,
  "turns": 2,
  "started_at": "2026-10-04T20:31:07.402Z",
  "resumed": false
}
```

`state` is `open`, `running` (a turn streams), `waiting` (the application
asked the person something) or `stopped`. A second turn while one runs is
refused (409), as is anything but `resume` on a stopped session.

## What answers

- **An application written as a spec** (or on the Canvas): every turn is a run
  of its agent, through the agent's own AG-UI app, with the rules, checks and
  record it was made with. The conversation so far goes with each turn; the
  settings, in words, with the first message after they changed; an action's
  payload, said as what the block gave — `On the page, select: {"row": {"region": "north"}}` — since a spec has no handler of its own.
- **An application written in Python** (an `app.py` of the catalogue): its
  code reacts, through an `AppHost` whose channel is the session.
  `session.send` and `session.stream` are `TEXT_MESSAGE_*` events,
  `session.step` is `STEP_STARTED` and `STEP_FINISHED`, and `session.agent`
  is the agent the runtime made for the application — its tools, its rules,
  its record.

## Files

A file given with an action is the session's, `{name, type, size, data_url}`
as File upload gives it, up to 25 MB:

- **An application whose permissions turn its shell on** has it put in its
  sandbox, at `files/<session uid>/<name>`, whatever its type and size; its
  agent is told where, and reads it in code: *The file report.pdf
  (application/pdf, 18 bytes) is in your sandbox at
  files/session-0002/report.pdf: read it in code.*
- **One without a shell** is given a text file in the message — `text/*`,
  JSON, XML, YAML, or a `.csv`, `.tsv`, `.txt`, `.md`, `.json`, `.jsonl`,
  `.xml`, `.yaml`, `.log`, up to 120,000 characters — and refuses anything
  else in a sentence, on the stream (`RUN_ERROR`): it has no computer to read
  it in.
- **A Python application** gets the file itself: it answers what the code
  asks with `session.ask(FileQuestion(...))`, whether it was given before the
  question or after, and a handler of the action finds it in its payload,
  under `files`.

## When the application asks

When the code asks the person something, the stream ends on the question: a
`CUSTOM` event named `loop.ask` — `{kind, prompt}` and, by kind, `options`,
`accept` and `max_bytes`, or `fields` — the question in words as a message,
then `RUN_FINISHED`. The session is `waiting`; the answer goes on the turn,
streamed on its own request:

| It asks | Answered by |
| --- | --- |
| text, a choice | a message |
| a file | an action with the file |
| a form (its fields are the settings) | a settings change |

Anything else while it waits is refused with what it waits for: *Report from a
File is waiting for an answer: Which file? (a file: .csv)*.

## Stop and resume

**Stop** cancels the turn and leaves the session stopped. A client that goes
away before the turn ends stops the turn only: the session stays open, which
is what the chat's stop button does.

**Resume** of a stopped session streams the conversation so far as a
`MESSAGES_SNAPSHOT`, runs a Python application's `resume`, and opens it again.
A session the runtime no longer holds — it restarted — is resumed from its
**record**: its `turn` entries, read from ai-agents with the caller's token,
become the conversation, and the record says *A session of … resumed* under
the same uid. An application whose record keeps no conversations cannot be
resumed so, and says it.

## Over AG-UI

`POST /api/v1/apps/agents/{agent}/ag-ui/` takes AG-UI's `RunAgentInput` and
answers its events, so any AG-UI front end drives an application's session.
The thread is the session. `forwardedProps.loop` carries what a page did
besides the message:

```json
{
  "threadId": "thread-0001",
  "runId": "run-1",
  "messages": [{"id": "m1", "role": "user", "content": "Run on report.pdf."}],
  "forwardedProps": {
    "loop": {
      "action": {"name": "upload", "payload": {}},
      "files": [{"name": "report.pdf", "type": "application/pdf", "size": 18, "data_url": "data:application/pdf;base64,…"}],
      "settings": {"tone": "Warm"}
    }
  }
}
```

This is what the chat of an application's page speaks: `ChatView` addresses an
application's agent here rather than at `/api/v1/ag-ui/{agent}/`, and the
embed's floating chat too. The page's buttons go with the chat's own run
(`viewControls.send(message, {loop})`), so what they start streams in the
conversation and in the page's `/status`, `/answer` and `/output`. The page
still handles only the buttons its kind does (`send`, `run`, `upload`, `stop`,
`new`); another action name reaches the session from a client of these
routes, or a Python application's own handler.

## What is verified, and what is not

**Verified** (`agent_runtimes/tests/test_app_sessions.py`, the real routes in
process on an agent made as the create route makes an application's, its
model scripted): a Preview session started, answered and recorded under its
uid as the person; a deployment's acting as its principal, and a Preview
refused on it; the chat's AG-UI run opening a session at its thread; a binary
file put in the sandbox of an application with a shell, a text file in the
message of one without, anything else refused; settings checked and kept;
stop and resume; resume from the record after the sessions are forgotten;
*Report from a File* taking its CSV from the page, asking for it when none was
given, and refusing a PDF. The page side is tested with vitest
(`app-page`, `app-page-blocks`, `embed-element`).

**Not verified.** No session has run on a cloud runtime yet: it needs the
runtime image rebuilt on this release. Anonymous visitors of a public
application are told apart only by being anonymous (R-30).
