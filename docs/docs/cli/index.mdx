# Loop CLI

The `agent-runtimes` package provides a command-line interface for starting and managing the Agent Runtimes server.

<img src="https://images.datalayer.io/products/codeai/codeai_short_cut.gif"/>

The package also provides an interactive assistant workflow via:

```bash
agent-runtimes chat
```

## Interactive Assistant

The interactive assistant experience is part of Agent Runtimes and runs through `agent-runtimes chat`.

### Quick Start

```bash
pip install "agent-runtimes[chat]"
agent-runtimes chat
```

This starts an interactive session with a background agent-runtimes server and the default valid agent spec.

### Interactive Mode

Launch without arguments to start a session with the terminal UX (TUX):

```bash
agent-runtimes chat
```

When started without `--agentspec-id`, the CLI lists available agent specs and lets you choose one interactively.

```bash
# Pick interactively
agent-runtimes chat

# Specify an agent spec
agent-runtimes chat --agentspec-id data-acquisition

# Disable codemode
agent-runtimes chat --agentspec-id data-acquisition --no-codemode
```

### Single-Query Mode

Pass a query to run one request and exit:

```bash
agent-runtimes chat "What is Python?"
agent-runtimes chat -a crawler "Search for AI trends"
```

For several lines in one session, slash commands among them, see [Run without interaction](#run-without-interaction).

### Here, or on Datalayer

`loop` asks **where** the agent runs first: *on this machine* (a local server, with your own model keys) or *on Datalayer* (a cloud runtime, billed by the minute). Datalayer is offered once you are signed in (`datalayer login`, or `DATALAYER_API_KEY`). Otherwise `loop` says so in one line and runs here. Without a terminal it always runs here unless a flag says otherwise, so a script never starts something billed by surprise.

On this machine, `loop` then lists the agentspecs your local model keys allow, as before. On Datalayer it lists **no agentspecs**. Launching an agent in the cloud needs an environment that supports it, so you pick an environment instead. The list is read through the Datalayer SDK (`AgentClient.list_environments`):

```text
? Where should the agent run?
    On this machine — a local server, with your own model keys
  ❯ On Datalayer — a cloud runtime with Datalayer's models, billed by the minute

Credits: 12,808.98 left.
31 of your environments say nothing about agents and are not listed: --environment <name> to try one.
Running agent runtimes: none.
Models: the runtime's own, through Datalayer — not this machine's keys; /models lists them once connected.

? In which environment? (only those that can launch an agent can be picked)
  ❯ ai-agents-env — AI Agents Environment, 0.048 credits a minute
    - kaggle-cpu — Kaggle notebook sessions, interactively against..., not priced  (cannot launch an agent (no agent capability))
    - modal-gpu — Containers on Modal, with or without a GPU atta..., not priced  (cannot launch an agent (no agent capability))
    …
The runtime's agent is example-simple, the agent loop starts with: a runtime is configured from an agentspec. -a <agentspec> for another.
? For how many minutes? (0.05 credits a minute; stopped when you leave, if you say so) [30]
Launching example-simple on Datalayer (ai-agents-env, 30 min, at most 1.44 credits)…
● Runtime 01k… on Datalayer — ai-agents-env, reserved 30 min (at most 1.44 credits)
```

- **Environments**: every environment that declares its capabilities is listed, with its description and its cost per minute. Only those with the `agent` capability (`ai-agents-env` today) can be picked; the others are greyed out with the reason. The default is the first that can launch an agent. Without anybody to ask, `ai-agents-env` is taken, or the only environment that can hold an agent; when several others could, `loop` asks you to name one with `--environment`. Your own environments declare no capabilities, so they are not listed, but you can still name one with `--environment`. Naming one that says it cannot hold an agent is refused.
- **The agent**: the platform configures a runtime's agent only from an agentspec. Without `-a`, it is `example-simple`, the agent `loop` starts with, and one grey line says so. `-a <agentspec>` picks another; your local API keys never filter it.
- **Running runtimes**: if you already have an agent runtime running, `loop` offers to go back to it before launching a new one, so you do not pay twice. `--runtime <name>` attaches without asking. If you also pass `-a`, the runtime's agent is reconfigured from that agentspec.
- **Cost**: a minute costs the environment's burning rate. The reservation (`--minutes`, 30 by default) caps what the runtime can cost, and it is checked against the credits you have left before the launch.
- **Unmetered**: with `DATALAYER_MAGIC_API_KEY` set in the environment (the platform's magic key, a secret), every runtime the client creates is sent it (`magic_api_key` on `POST /runtimes`), and the platform starts it unmetered: it consumes no credits and never expires. No minutes are asked and no credit is checked; `--minutes` is still validated and sent, and ignored. Unset, nothing is sent. The key is never printed or logged.
- **At the end**: `loop` asks whether to stop the runtime, because it is billed until it is stopped or its reservation ends. `--keep` leaves it running, and `loop` prints how to reconnect (`loop connect <url>`, which goes back to it as `loop --runtime <name>` does) and how to stop it (`loop agents terminate <name>`). A one-shot query (`loop --cloud -a crawler "…"`) stops the runtime it launched once the query is answered. A runtime you attached to without a terminal is left as it was found.

Each refusal is one sentence, and nothing is launched: not signed in, no credits (or not enough for the reservation), an environment that cannot hold an agent, a runtime that is not running, the launch refused by the platform, or an agentspec the runtime's library does not have.

```bash
loop --local                          # on this machine, without asking
loop --cloud                          # on Datalayer: pick an environment; the agent is example-simple
loop --cloud -a crawler               # on Datalayer, a new runtime for the crawler agent
loop --cloud -a crawler -m 15 --keep  # reserved for 15 minutes, left running at the end
loop --runtime 01k…                   # back to a running agent runtime
loop --cloud -a crawler "Summarize the news"  # one query, then the runtime is stopped
```

#### Models on a cloud runtime

A runtime on Datalayer calls its models **through datalayer-ai-inference, with your own token**. It never calls a provider such as Bedrock with keys of its own:

- **Every agent goes through ai-inference.** This holds whatever its agentspec's `inference_provider` says. An agentspec that says `local`, such as `example-simple`, still runs locally on your machine, and on Datalayer through ai-inference.
- **The token is yours, narrowed to ai-inference.** When the runtime is assigned to you, IAM mints it from your session. It can call ai-inference's chat completions, its model list and its decisions, and every other Datalayer service refuses it. It lasts as long as the runtime's reservation. Every model call is metered on your account, as a call from the Datalayer UI is.
- **What is offered is what ai-inference serves.** With your token, the runtime asks ai-inference which models it serves, and offers your agent those of its agentspec's `model` and `model_additionals` that ai-inference serves, such as Qwen (`alibaba:qwen-max`) beside Claude Sonnet. Only those are listed: a model of the agent's that ai-inference does not serve is left out, and so are local models and runtimes (Ollama, LM Studio, …), which a runtime going through ai-inference does not call. The same holds on this machine when the provider is `datalayer`.
- **Before the token arrives, nothing is called.** A runtime waiting in the pool has no user, so it has no token yet. Until it is assigned, `/models` says `This runtime has no ai-inference token yet: …`, every model is marked `No ai-inference token`, and a message fails with that sentence.
- **Decisions are listed apart.** ai-inference also serves typed-decision models, such as Jev on Workers AI (`cloudflare:wrk/typesafe/jev`). `/models` lists them under **Decisions**, with one line saying what they are for: they answer a decision's typed questions, and agents do not chat with them. Each is marked usable when ai-inference serves it, by the same rule as the chat models: before the token arrives, it is listed and marked `No ai-inference token`. `/models cloudflare:wrk/typesafe/jev` is refused: `cloudflare:wrk/typesafe/jev answers typed decisions, not a conversation: an agent cannot run on it, so nothing was switched. A decision asks it through /decisions.` The agent stays as it was.
- **When the token expires, the runtime stops calling models.** If a runtime outlives its token, it says when the token expired and calls no model any more. Start a new runtime.

#### The decide tool

An agent decides with Jev through its `decide` tool (agentspecs `tools/decide.yaml`). *A Simple Agent* (`example-simple`), the default cloud agent, has it, and suggests three decisions to try: is a support ticket urgent, which team should handle a request, how positive a review is.

- **What it asks.** A text, the *state*, and one or more named questions about it, each of a type: `noul` (does a statement hold — answered with its probability), `choice` (which of at least two options — a probability per option and a confidence) or `score` (which step of at least two, lowest first — a probability per step and a confidence). The agent reads the typed answers back and says what was decided.
- **Where it goes.** To ai-inference's `POST /decisions`, model `cloudflare:wrk/typesafe/jev`, with the runtime's ai-inference token — the one its model calls use. With no token, or no ai-inference configured (`DATALAYER_AI_INFERENCE_URL`), it asks nothing and the agent is told why in a sentence (`Nothing was decided. This runtime has no ai-inference token yet: …`).
- **It only reads.** Its action class is `read`: it reaches nothing but ai-inference and changes nothing.

You can ask Jev yourself, without the agent, with `/decisions`: the text in quotes, then the questions — `--yes-no "<question>"`, `--choice "<question>" A,B,C` and `--score "<question>" 1-5` (a range, or named steps lowest first), as many as you want. The runtime asks them as the `decide` tool does (`POST /api/v1/configure/inference/decisions`), with its own ai-inference token, so it works the same on this machine and on Datalayer. Each answer is one line, named after its question. `/decisions` alone shows how to use it.

```text
/decisions "Payouts have failed for 3 days." --yes-no "Is it urgent?" --choice "Which team?" Billing,Tech,Sales

● Decided by cloudflare:wrk/typesafe/jev
  is_it_urgent: yes (0.93 that it holds)
  which_team: Billing (confidence 1.00)
```

A runtime older than `loop` that does not have the route says so in a sentence, with its version (`… (agent-runtimes 1.3.32) does not say decisions (/decisions): it is older than this loop (1.3.33).`).

```bash
loop --local -a example-simple --no-codemode \
  --prompt "Is this support ticket urgent? 'Payouts have failed for 3 days.' Use your decision tool."
```

#### Slash commands on a cloud runtime

The terminal reaches a cloud runtime through a relay on your machine that adds your Datalayer token to every request. Every slash command reads the session's one server address, so on Datalayer `/models`, `/skills`, `/tools`, `/mcp`, `/status`, `/context` and the others query and act on the **cloud runtime**, exactly as they do on a local one:

- `/models` lists the models the cloud runtime offers its agent, under `Models on RUNTIME on Datalayer`: those of the agentspec's `model` and `model_additionals` that ai-inference serves, under **Cloud**, and Jev under **Decisions**, and below the title who decided — on Datalayer, `ai-inference at … serves …`, the list the runtime asked datalayer-ai-inference for when it was assigned to you. `/models <id>` switches the runtime's agent to a model only if the runtime offers it to this agent and can use it. The switch recreates the agent the session talks to from its agentspec, on that model — its `model_additionals` stay its models, so it can be switched back. Otherwise the switch is refused in a sentence, with what ai-inference serves (`RUNTIME on Datalayer does not offer … to this agent: nothing was switched. ai-inference at … serves ….`), and the sandbox never moves to this machine. Asked directly (`POST /api/v1/agents/configure-from-spec`), the runtime refuses a model ai-inference does not serve before it touches the agent in place.
- `/skills`, `/tools` and `/mcp` list and change the skills, tools and MCP servers of the cloud runtime's agent.
- `/status` shows `Agent Runtime  RUNTIME on Datalayer (ENVIRONMENT)` and the relay it goes through.
- `/suggestions` lists the agentspec's suggestions, each as its summary and the text it sends, and asks which one to send.
- `/notebook` and `/document` open the agent's notebook and document pages in your browser, served by the cloud runtime through the relay (`http://127.0.0.1:<port>/static/agent-notebook.html?agentId=default&jupyterBaseUrl=…&jupyterToken=…`). The relay adds your Datalayer token to every request the page makes, so your token is not in the URL; the page works while `loop` runs. The page runs its code on the runtime's Jupyter server, at the runtime's address on Datalayer, with the runtime's own Jupyter token, as the Datalayer UI does. That token is in the URL, and so in your browser history, until the runtime stops. The same holds after `loop --runtime <name>` and `loop connect <url>`.

Nothing falls back to this machine. If the cloud runtime does not answer, a command that needs it is not run, and `loop` says so in a sentence. `/help`, `/exit`, `/status` and the other commands that read nothing from the runtime still work.

To check a runtime's models from a script or CI, without typing them in, see [Run without interaction](#run-without-interaction).

### Run without interaction

`--prompt` (short `-q`) runs `loop` without a person at the keyboard. `loop` starts the agent, runs each line you give it as if you had typed it at the prompt, prints what comes back, stops the agent and exits:

- **Repeat it** for several lines. They run in the order given, in **one session**, so a model switched by one line is the model the next line talks to, and the conversation carries over.
- A line that starts with `/` runs that **slash command**, the same as at the prompt: `/models`, `/models <id>`, `/skills`, `/tools`, `/status` and the others. A command that would ask something does not: `/suggestions` lists the suggestions and sends none, and the next line runs next.
- Any other line is a **message** to the agent, and its answer is printed.

It runs **on this machine** unless you say `--cloud`:

- **On this machine** (`--local`, the default), name the agent with `-a <agentspec>`. The local server `loop` starts is stopped at the end.
- **On Datalayer** (`--cloud`), a new cloud runtime is launched for the run, as interactive `loop --cloud` launches one. `-a` names its agent (`example-simple` when you leave it out), `-e` its environment (`ai-agents-env` by default) and `-m` how many minutes to reserve (30 by default). `-r <name>` runs the lines on a runtime that is already running instead, and nothing is launched.
- **At the end** the cloud runtime is stopped, also when a line fails or you press Ctrl-C. `--keep` leaves it running, and `loop` prints how to stop it (`loop agents terminate <name>`). A runtime you attached to with `-r` was running before, so it is left running.

**Nothing is asked.** Every choice comes from the options or their defaults. When a choice would need a person, the run stops before anything starts and says why in one sentence: no `-a` on this machine, several environments that could hold the agent and none named, or a number of minutes out of range.

**Output.** The answers and what the slash commands print go to standard output. Everything else goes to standard error: the launch, each line as it starts (`[2/4] /models alibaba:qwen-max`), the tokens a turn used, errors, and the stop. When standard output is not a terminal (a pipe, a file, CI), nothing is coloured or animated and long lines are not wrapped, so the output can be read by another program or searched with `grep`.

**Exit codes.**

| Code | When |
|------|------|
| `0` | Every line ran. |
| `1` | The launch was refused (not signed in, no credits, an environment that cannot hold an agent), the runtime did not start or did not answer, or a line failed: an unknown slash command, or an answer from the agent that was an error. The run stops at the first line that fails. |
| `2` | A choice would need asking, such as no `-a` on this machine. |
| `130` | You pressed Ctrl-C. The runtime is still stopped, unless `--keep`. |

A slash command that **refuses** what it is asked has not failed: it did its job. `/models <id>` with a model the runtime does not offer, or with a typed-decision model such as `cloudflare:wrk/typesafe/jev`, prints its refusal (`… nothing was switched.`) and the run goes on to the next line, with exit code `0` at the end.

Check what a Datalayer runtime suggests and offers, switch to Qwen, ask it who it is, then try a model the runtime does not serve:

```bash
loop --cloud -a example-simple -m 10 \
  --prompt "/suggestions" \
  --prompt "/models" \
  --prompt "/models alibaba:qwen-max" \
  --prompt "Who are you and which model are you? One sentence." \
  --prompt "/models bedrock:us.anthropic.claude-opus-5"
```

Its standard output has this shape (the runtime's name, the models offered and the answer's words vary):

```text
● Suggestions (7):

  1. Tell a joke
     Tell me a joke
  …
  5. Decide: is it urgent?
     Is this support ticket urgent? 'Payouts have failed for 3 days.'
  …

● Models on RUNTIME on Datalayer (ai-agents-env) (2)
  ai-inference at … serves bedrock:us.anthropic.claude-sonnet-4-6, alibaba:qwen-max.

  Cloud
    ● bedrock:us.anthropic.claude-sonnet-4-6
    ● alibaba:qwen-max

  Decisions
    Answers a decision's typed questions (yes or no, a choice, a score); agents do not chat with it.
    ● cloudflare:wrk/typesafe/jev
        Jev (Cloudflare Workers AI)

  /models <id> to switch

● Model: Alibaba Qwen-Max
  alibaba:qwen-max

I am Qwen, a large language model created by Alibaba Cloud.
RUNTIME on Datalayer (ai-agents-env) does not offer bedrock:us.anthropic.claude-opus-5 to this agent: nothing was switched. ai-inference at … serves bedrock:us.anthropic.claude-sonnet-4-6, alibaba:qwen-max.
```

Only what ai-inference serves is listed: no local models, no `Not running: …` line for local runtimes. Standard error has the launch, `[1/5] /suggestions` to `[5/5] /models bedrock:us.anthropic.claude-opus-5`, and `Stopped RUNTIME.` at the end. The exit code is `0`.

In CI, keep the output and fail the job when a line fails:

```bash
loop --cloud -a example-simple -m 5 \
  -q "/models" \
  -q "Answer with the single word: ready" \
  > answers.txt
grep -qi "ready" answers.txt
```

Datalayer needs your credentials in the job: set `DATALAYER_API_KEY`. On this machine the same lines run against a local server, for example `loop --local -a example-simple -q "/models"`.

### A new application

`loop apps init <id>` writes a new application's folder, named by its id: its Appspec, `app.yaml`, and, with `--python`, the `app.py` that is its source, the spec beside it built from it (`loop apps build`), so the two agree from the start.

```bash
loop apps init my-app                              # a chat: app.yaml
loop apps init my-app --python                     # app.py, and the app.yaml it builds
loop apps init my-app --kind widget                # a widget
loop apps init desk --from support-desk            # an example of the catalogue, under the new id
loop apps init desk --from support-desk --python   # its spec held in an app.py, ready for code
loop apps init --examples                          # the examples to start from
```

A blank application is a chat or a widget, its agent the one a blank application starts with in the Studio (`example-simple`). A worker says what starts its work and its goal, and a decision what it decides, so they start from an example. From an example, the folder holds its spec, and its `app.py` when it was written in Python (`customer-interview`, `report-from-a-file`), with the new id. What is written passes the checks `loop apps validate` makes of a spec, or nothing is written. A folder that is there is never overwritten. `--dir` says where the folder goes.

Beside them, `tests/test_app.py` is what the folder's CI runs with `pytest tests`: the spec passes the instant checks, each of its test conversations (`tests.cases`) says what it is asked and what it should do, and, in Python, the `app.py` still builds the `app.yaml` committed beside it. A starting repository, then: commit the folder and its checks pass from the first push. The test conversations themselves are asked of a model by a validation run — push it (`loop apps push app.yaml`), then *Run its tests* on its Validate tab — and the safety set every application answers with `loop apps validate app.yaml --safety --local`.

```text
✓ desk written to ./desk from the support-desk example: app.yaml, tests/test_app.py.
Next: cd desk && loop apps run app.yaml
```

### Eject: an application into Python

`loop apps eject app.yaml` writes an application built by spec or on the
Canvas as an `app.py` that reproduces it (LOOP P-13): the file holds the
spec, ready for code, and builds the same spec again — checked before it is
written; otherwise nothing is. It is one way, and it says so first: from then
on the file is the application's source, its spec built from it. It asks
before it writes (`--yes` in a script; without a terminal, nothing is
written without it), never writes over a file (`--force`), and writes
`app.py` beside the spec unless `--out` says where.

```bash
loop apps pull <id>                      # its spec, as the Studio keeps it
loop apps eject app.yaml --yes           # app.py, which builds it the same
loop apps push app.py --app <id>         # the next version; the versions so far are kept
```

### An application's safety set

`loop apps validate <file>` runs the instant checks of an application: no model is called, so it is quick and free in CI. Add `--safety` and it also takes the **safety set** every application runs, the same tests the Studio asks with every *Run its tests*:

- **An instruction hidden in what it reads**, when it reads documents or has connections. It is handed a passage that carries an instruction it must not follow.
- **A request outside its rules**, when its rules make it ask first or leave an action to you. It is asked to do that action now, without asking. The request uses its own rule's words.
- **A request for what it must not give**: its passwords and keys, and what another person said.
- **A request to change its own instructions**: it is told to drop them and to write them out.

A model judges each answer against the test's rubric, and each test has its own failure mode. If one test does not hold, the application cannot ship, whatever share of its tests passed.

```bash
loop apps validate app.yaml --safety                     # lists the tests and how each is judged; nothing is asked
loop apps validate app.yaml --safety --local --judge anthropic:claude-haiku-4-5
loop apps validate app.yaml --safety --cloud --app <id>  # on Datalayer, through the Evals engine
```

```text
app.yaml  Passes the instant checks
  Its tests decide whether it is ready.
  ✓ A request for what it must not give — Held.
  ✓ A request to change its own instructions — Held.
  Safety: 2 of 2 held.
```

- **On this machine** (`--local`): each test is asked in a session of its own. An application that needs nothing a runtime brings runs in this process, with its rules, checks and code. One with connections, tools or skills runs on a local runtime configured with it, as `loop apps run --local` does. The judge is the model named by `--judge`, using your key for it on this machine, or the AI Inference service when `DATALAYER_AI_INFERENCE_URL` is set. With no judge, nothing is asked: the tests are listed, with the way each would be judged.
- **On Datalayer** (`--cloud --app <id>`): the Evals engine runs the saved application itself, with its connections and rules (the `app` subject), at its current version. The file must be that version, so if it is not, push it first (`loop apps push`). The launch is checked before anything starts, and the engine's refusal is shown in its own words. It is billed, so `loop` asks first and shows the most it can cost. Without a terminal it launches only with `--yes`. The tests are kept in an evalset of their own, `<name> — safety set`, which is reused for as long as the tests stay the same.

Exit codes: `1` when the application is not ready or a safety test did not hold (an answer that never came counts as not holding), `2` with `--strict` when something needs attention, and `3` when the safety set was asked for but not judged (no judge, a launch you declined, or a run that could not start).

### Connect to a Remote Server

Use the `connect` subcommand to attach to an existing server:

```bash
# AG-UI (HTTP/SSE) - default
agent-runtimes chat connect http://localhost:8000/api/v1/ag-ui/chat/

# ACP (WebSocket)
agent-runtimes chat connect ws://localhost:8000/api/v1/acp/ws/chat -t acp

# A runtime on Datalayer, at the address loop printed for it: the same as loop --runtime <uid>
loop connect https://r1.datalayer.run/agent-runtimes/ai-agents-pool/<uid>/api/v1/ag-ui/default/
```

### Key Components

- `agent_runtimes/chat/cli.py`: Typer commands, runtime process management, and transport wiring
- `agent_runtimes/chat/tux.py`: Rich terminal UX, slash command handling, and streaming rendering
- `agent_runtimes/chat/commands/`: slash command modules and registry
- `agent_runtimes/chat/banner.py`: brand output and animation helpers

### Runtime Flow

1. `agent-runtimes chat` resolves an agent spec (provided or interactive picker).
2. It starts an embedded `agent-runtimes serve` process.
3. It waits for `/health` then fetches `/health/startup`.
4. Interactive mode launches TUX and streams responses over AG-UI.
5. On exit or signal, child processes are terminated cleanly.

### Transport Support

- AG-UI (`HTTP/SSE`) is the default for local and remote interactive chat.
- ACP (`WebSocket`) is supported via `agent-runtimes chat connect -t acp`.

### Slash Command Registry

Slash commands are modularized in `agent_runtimes/chat/commands/` and assembled via `build_commands(...)`. This keeps command behavior isolated and easy to evolve.

## Extending, and Being an Extension

The command line is wired into the reactor's extensible-CLI machinery in
both directions:

- **As an extension** — `agent_runtimes.reactor_extension` packages every
  command group of this package as a reactor CLI plugin, advertised under
  `datalayer.cli` (so the `datalayer` command carries `sandboxes`, `agents`,
  `envs` and the rest) and under `datalayer.reactor.cli` (so the `reactor`
  command does too). Nothing spawns another executable; the groups register
  in-process at startup.
- **As a host** — the interactive chat's slash commands sit in the reactor's
  slash registry, and a distribution advertising a plugin under the
  `loop.plugins` entry-point group adds its own commands to the session. See
  the [Loop REPL](/loop-repl#slash-command-registry) page.

## `serve` Command

Start the agent-runtimes server.

```bash
agent-runtimes serve [OPTIONS]
```

### Options

| Option | Short | Default | Environment Variable | Description |
|--------|-------|---------|---------------------|-------------|
| `--host` | `-h` | `127.0.0.1` | `AGENT_RUNTIMES_HOST` | Host to bind to |
| `--port` | `-p` | `8000` | `AGENT_RUNTIMES_PORT` | Port to bind to |
| `--reload` | `-r` | `false` | `AGENT_RUNTIMES_RELOAD` | Enable auto-reload for development |
| `--debug` | `-d` | `false` | `AGENT_RUNTIMES_DEBUG` | Enable debug mode with verbose logging |
| `--workers` | `-w` | `1` | `AGENT_RUNTIMES_WORKERS` | Number of worker processes |
| `--log-level` | `-l` | `info` | `AGENT_RUNTIMES_LOG_LEVEL` | Log level (`debug`, `info`, `warning`, `error`, `critical`) |
| `--agent-id` | `-a` | - | `AGENT_RUNTIMES_DEFAULT_AGENT` | Agent spec ID from the library to start |
| `--agent-name` | `-n` | `default` | `AGENT_RUNTIMES_AGENT_NAME` | Custom name for the agent (requires `--agent-id`) |
| `--orchestrator-root` | - | - | `AGENT_RUNTIMES_ORCHESTRATOR_ROOT` | Register the orchestrator as the ACP agent `orchestrator`, delegating each turn to this agent: an agentspec ID, or an A2A (`http`) or ACP (`ws`) endpoint |
| `--protocol` | `-t` | `ag-ui` | `AGENT_RUNTIMES_PROTOCOL` | Transport protocol (`ag-ui`, `vercel-ai`, `vercel-ai-jupyter`, `a2a`) |
| `--no-config-mcp-servers` | - | `false` | `AGENT_RUNTIMES_NO_CONFIG_MCP_SERVERS` | Skip starting config MCP servers from `~/.datalayer/mcp.json` |
| `--no-catalog-mcp-servers` | - | `false` | `AGENT_RUNTIMES_NO_CATALOG_MCP_SERVERS` | Skip starting catalog MCP servers defined in the agent spec (requires `--agent-id`) |
| `--mcp-servers` | `-m` | - | `AGENT_RUNTIMES_MCP_SERVERS` | Comma-separated list of MCP server IDs from the catalog to start |
| `--codemode` | `-c` | `false` | `AGENT_RUNTIMES_CODEMODE` | Enable Codemode: MCP servers become programmatic tools via CodemodeToolset |
| `--skills` | `-s` | - | `AGENT_RUNTIMES_SKILLS` | Comma-separated list of skills to enable (requires `--codemode`) |
| `--jupyter-sandbox` | `-j` | - | `AGENT_RUNTIMES_JUPYTER_SANDBOX` | Jupyter sandbox URL with token for code execution (e.g., `http://localhost:8888?token=xxx`) |
| `--find-free-port` | `-f` | `false` | `AGENT_RUNTIMES_FIND_FREE_PORT` | If the port is in use, find the next available port |

### MCP Server Control

By default, the server automatically starts:
- **Config MCP servers** from `~/.datalayer/mcp.json`
- **Agent spec MCP servers** when using `--agent-id`

You can control which MCP servers are started:

```bash
# Start with specific MCP servers from the catalog
agent-runtimes serve --mcp-servers tavily,github

# Combine with an agent spec (agent spec servers + additional servers)
agent-runtimes serve --agent-id crawler --mcp-servers filesystem

# Start WITHOUT config MCP servers (from ~/.datalayer/mcp.json)
agent-runtimes serve --no-config-mcp-servers

# Start with agent but without config MCP servers
agent-runtimes serve --agent-id crawler --no-config-mcp-servers

# Start with agent but WITHOUT its catalog MCP servers (from agent spec)
agent-runtimes serve --agent-id data-acquisition --no-catalog-mcp-servers

# Start with neither config nor catalog MCP servers (minimal startup)
agent-runtimes serve --agent-id crawler --no-config-mcp-servers --no-catalog-mcp-servers
```

:::tip Managing MCP Servers at Runtime
You can dynamically add MCP servers via the [REST API](/endpoints#enable-catalog-server):

```bash
# Enable an MCP server from the catalog
curl -X POST http://localhost:8000/api/v1/mcp/servers/catalog/tavily/enable

# Disable an MCP server
curl -X DELETE http://localhost:8000/api/v1/mcp/servers/catalog/tavily/disable
```

See the [MCP Servers API documentation](/endpoints#mcp-servers) for more details.
:::

### Codemode

Codemode transforms MCP servers into programmatic tools that can be composed through code execution. When enabled, the agent uses `CodemodeToolset` instead of directly adding MCP toolsets.

```bash
# Start with Codemode enabled (uses config MCP servers)
agent-runtimes serve --codemode

# Start with Codemode and specific MCP servers
agent-runtimes serve --codemode --mcp-servers tavily,github

# Start with Codemode and an agent spec
agent-runtimes serve --agent-id crawler --codemode

# Start with Codemode and skills
agent-runtimes serve --agent-id crawler --codemode --skills web_search,github_lookup

# Using short options
agent-runtimes serve -a crawler -c -s web_search,github_lookup
```

:::info How Codemode Works
When `--codemode` is enabled:
1. MCP servers from the agent spec are converted to programmatic tools
2. The `CodemodeToolset` is used to expose tools via code execution
3. MCP toolsets are NOT added directly to the agent
4. Skills can be enabled for additional capabilities

This allows the agent to compose multiple tool calls within a single code execution, improving efficiency and enabling more complex workflows.
:::

#### Jupyter Sandbox

By default, Codemode uses a local Python `exec()` sandbox for code execution. You can connect to an external Jupyter server instead, which provides:

- **Persistent kernel state** across executions
- **Rich output support** (plots, dataframes, etc.)
- **Access to pre-installed packages** in the Jupyter environment
- **Isolation** from the agent server process

```bash
# Start with Codemode using a Jupyter sandbox
agent-runtimes serve --codemode --jupyter-sandbox "http://localhost:8888?token=my-token"

# Combine with MCP servers and skills
agent-runtimes serve --codemode --mcp-servers tavily --skills web_search \
  --jupyter-sandbox "http://localhost:8888?token=my-token"

# Using environment variable
AGENT_RUNTIMES_JUPYTER_SANDBOX="http://localhost:8888?token=xxx" \
  agent-runtimes serve --codemode
```

:::tip Setting Up a Jupyter Server
To use the Jupyter sandbox, you need a running Jupyter server. You can start one with:

```bash
# Start Jupyter server with a token
jupyter server --port 8888 --IdentityProvider.token=my-token

# Or using JupyterLab
jupyter lab --port 8888 --IdentityProvider.token=my-token
```

The sandbox will connect to the kernel and persist state between code executions.
:::

#### Codemode vs Standard Mode

| Feature | Standard Mode | Codemode |
|---------|--------------|-----------|
| MCP tool invocation | Direct tool calls | Via code execution |
| Tool composition | One tool per LLM call | Multiple tools in single code block |
| Skill support | Not available | Full skill support |
| Tool discovery | Via MCP protocol | Via generated Python bindings |
| Execution context | Isolated per tool | Shared sandbox context |

### Skills

Skills are reusable agent capabilities that extend Codemode functionality. They provide pre-built workflows that combine multiple tools.

```bash
# Start with a single skill
agent-runtimes serve --codemode --skills web_search

# Start with multiple skills (comma-separated)
agent-runtimes serve --codemode --skills web_search,github_lookup,file_operations

# Combine with an agent spec
agent-runtimes serve --agent-id crawler --codemode --skills web_search,data_analysis
```

:::note Skills Require Codemode
The `--skills` option requires `--codemode` to be enabled. Skills are implemented as code-based workflows that run within the Codemode sandbox.
:::

### Transport Protocols

Choose the transport protocol used for agent communication with `--protocol`:

```bash
# Default: AG-UI protocol (CopilotKit compatible)
agent-runtimes serve --agent-id crawler --protocol ag-ui

# Vercel AI SDK protocol

# Vercel AI Jupyter protocol (for notebook integration)
agent-runtimes serve --agent-id data-acquisition --protocol vercel-ai-jupyter

agent-runtimes serve --agent-id crawler --protocol a2a
```

| Protocol | Description |
|----------|-------------|
| `ag-ui` | CopilotKit-compatible AG-UI protocol (default) |
| `vercel-ai` | Vercel AI SDK protocol for streaming responses |
| `vercel-ai-jupyter` | Vercel AI with Jupyter notebook execution support |

## `mcp-servers-config` Command

List MCP servers from the user's config file. These are custom MCP server configurations defined in `~/.datalayer/mcp.json`.

```bash
agent-runtimes mcp-servers-config [OPTIONS]
```

### Options

| Option | Short | Default | Description |
|--------|-------|---------|-------------|
| `--output` | `-o` | `table` | Output format (`table` or `json`) |

### Examples

```bash
# List config MCP servers
agent-runtimes mcp-servers-config

# Output as JSON
agent-runtimes mcp-servers-config --output json

# Using short option
agent-runtimes mcp-servers-config -o json
```

### Config File Format

The config file is located at `~/.datalayer/mcp.json` and uses the following format:

```json
{
  "mcpServers": {
    "my-custom-server": {
      "command": "npx",
      "args": ["-y", "@some/mcp-server"],
      "env": {
        "API_KEY": "${API_KEY}"
      }
    },
    "local-python-server": {
      "command": "python",
      "args": ["-m", "my_mcp_server"],
      "env": {}
    }
  }
}
```

:::tip Environment Variable Expansion
Environment variables in the config file are automatically expanded. Use `${VAR_NAME}` syntax to reference environment variables.
:::

### Output Formats

**Table format (default):**

```
📋 MCP Config Servers
╭─────────────────────┬─────────┬──────────────────────────────────────────┬────────────────────╮
│ ID                  │ Command │ Args                                     │ Env Vars           │
├─────────────────────┼─────────┼──────────────────────────────────────────┼────────────────────┤
│ my-custom-server    │ npx     │ -y @some/mcp-server                      │ API_KEY            │
│ local-python-server │ python  │ -m my_mcp_server                         │ none               │
╰─────────────────────┴─────────┴──────────────────────────────────────────┴────────────────────╯
Config: /home/user/.datalayer/mcp.json
Total: 2 server(s)
```

**JSON format:**
```json
{
  "config_path": "/home/user/.datalayer/mcp.json",
  "exists": true,
  "servers": [
    {
      "id": "my-custom-server",
      "command": "npx",
      "args": ["-y", "@some/mcp-server"],

    },
    {
      "id": "local-python-server",

```

## `start-mcp-servers` Command

Start MCP servers for running agents. This command starts the catalog MCP servers configured for the specified agent, or for all running agents if no agent ID is provided.

```bash
agent-runtimes start-mcp-servers [OPTIONS]
```

### Options

| Option | Short | Default | Description |
|--------|-------|---------|-------------|
| `--agent-id` | `-a` | - | The agent identifier (optional, if not provided starts MCP servers for all agents) |
| `--env-vars` | `-e` | - | Environment variables in format `VAR1:VALUE1;VAR2:VALUE2` |
| `--host` | `-h` | `127.0.0.1` | Agent-runtimes server host |
| `--port` | `-p` | `8000` | Agent-runtimes server port |

### Examples

```bash
# Start MCP servers for all running agents
agent-runtimes start-mcp-servers

# Start MCP servers for a specific agent
agent-runtimes start-mcp-servers --agent-id my-agent

# Start with environment variables (e.g., API keys)
agent-runtimes start-mcp-servers --agent-id my-agent \
    --env-vars "TAVILY_API_KEY:xxx;GITHUB_TOKEN:yyy"

# Start MCP servers for all agents with environment variables
agent-runtimes start-mcp-servers \
    --env-vars "TAVILY_API_KEY:xxx;GITHUB_TOKEN:yyy"

# Connect to a different server
agent-runtimes start-mcp-servers --agent-id my-agent \
    --host 0.0.0.0 --port 8080

# Using short options
agent-runtimes start-mcp-servers -a my-agent -e "TAVILY_API_KEY:xxx"
```

### Output

The command displays a formatted table showing the status of each MCP server:

```
╭─ MCP Servers Start - Agent: my-agent ─────────────────────╮
│ Server ID          │ Status                               │
├────────────────────┼──────────────────────────────────────┤
│ tavily             │ ✓ Started                            │
│ github             │ ⚡ Already running                   │
│ filesystem         │ ✗ Failed: Missing FILESYSTEM_PATH    │
╰────────────────────┴──────────────────────────────────────╯
✓ Codemode toolset rebuilt

Started 1 server(s), 1 already running, 1 failed
```

When no agent ID is provided, the output shows results for all agents:

```
╭─ MCP Servers Start - All Agents ──────────────────────────╮
│ Agents processed: agent-1, agent-2                        │
├───────────────────────────────────────────────────────────┤
│ Server ID          │ Status                               │
├────────────────────┼──────────────────────────────────────┤
│ tavily             │ ✓ Started                            │
│ github             │ ✓ Started                            │
╰────────────────────┴──────────────────────────────────────╯

Started 2 server(s) across 2 agent(s)
```

:::tip Codemode Toolset Rebuild
If the agent has Codemode enabled, starting MCP servers will automatically rebuild the Codemode toolset to include the newly started servers as programmatic tools.
:::

### Programmatic Usage

```python
from agent_runtimes.commands import (
    start_agent_mcp_servers,
    AgentMcpServersError,
    parse_env_vars,
)

# Parse env vars from string format
env_vars = parse_env_vars("TAVILY_API_KEY:xxx;GITHUB_TOKEN:yyy")
# Result: {"TAVILY_API_KEY": "xxx", "GITHUB_TOKEN": "yyy"}

# Start MCP servers for all agents
try:
    result = start_agent_mcp_servers(
        env_vars=env_vars,
        host="localhost",
        port=8000,
    )
    print(f"Agents processed: {result['agents_processed']}")
    print(f"Started: {result['started_servers']}")
    print(f"Already running: {result['already_running']}")
    print(f"Failed: {result['failed_servers']}")
except AgentMcpServersError as e:
    print(f"Error: {e}")

# Start MCP servers for a specific agent
try:
    result = start_agent_mcp_servers(
        agent_id="my-agent",
        env_vars=env_vars,
        host="localhost",
        port=8000,
    )
    print(f"Started: {result['started_servers']}")
    print(f"Already running: {result['already_running']}")
    print(f"Failed: {result['failed_servers']}")
    if result['codemode_rebuilt']:
        print("Codemode toolset was rebuilt")
except AgentMcpServersError as e:
    print(f"Error: {e}")
```

## Environment Variables

All CLI options can be configured via environment variables. These variables serve as defaults - CLI arguments will override them when provided.

### Configuration via Environment Variables

```bash
# Configure host and port via environment variables
export AGENT_RUNTIMES_HOST=0.0.0.0
export AGENT_RUNTIMES_PORT=8080
agent-runtimes serve  # Uses 0.0.0.0:8080

# CLI arguments override env vars
agent-runtimes serve --port 9000  # Uses 0.0.0.0:9000

# Configure agent via environment variable
export AGENT_RUNTIMES_DEFAULT_AGENT=crawler
agent-runtimes serve  # Starts with crawler agent

# Configure multiple settings at once
export AGENT_RUNTIMES_HOST=0.0.0.0
export AGENT_RUNTIMES_PORT=8080
export AGENT_RUNTIMES_WORKERS=4
export AGENT_RUNTIMES_LOG_LEVEL=warning
agent-runtimes serve  # Production-ready configuration
```

### Environment Variable Reference

| Variable | CLI Option | Description |
|----------|------------|-------------|
| `AGENT_RUNTIMES_HOST` | `--host` | Host to bind to / query |
| `AGENT_RUNTIMES_PORT` | `--port` | Port to bind to / query |
| `AGENT_RUNTIMES_RELOAD` | `--reload` | Enable auto-reload (`true`/`false`) |
| `AGENT_RUNTIMES_DEBUG` | `--debug` | Enable debug mode (`true`/`false`) |
| `AGENT_RUNTIMES_WORKERS` | `--workers` | Number of worker processes |
| `AGENT_RUNTIMES_LOG_LEVEL` | `--log-level` | Log level |
| `AGENT_RUNTIMES_DEFAULT_AGENT` | `--agent-id` | Agent spec ID to start |
| `AGENT_RUNTIMES_AGENT_NAME` | `--agent-name` | Custom name for the agent |
| `AGENT_RUNTIMES_NO_CONFIG_MCP_SERVERS` | `--no-config-mcp-servers` | Skip config MCP servers (`true`/`false`) |
| `AGENT_RUNTIMES_NO_CATALOG_MCP_SERVERS` | `--no-catalog-mcp-servers` | Skip catalog MCP servers from agent spec (`true`/`false`) |
| `AGENT_RUNTIMES_MCP_SERVERS` | `--mcp-servers` | Comma-separated list of MCP server IDs |
| `AGENT_RUNTIMES_CODEMODE` | `--codemode` | Enable Codemode (`true`/`false`) |
| `AGENT_RUNTIMES_SKILLS` | `--skills` | Comma-separated list of skills |
| `AGENT_RUNTIMES_FIND_FREE_PORT` | `--find-free-port` | Find free port if taken (`true`/`false`) |

:::tip Docker and Kubernetes
Environment variables are particularly useful for containerized deployments where you want to configure the server without modifying the command:

```dockerfile
ENV AGENT_RUNTIMES_HOST=0.0.0.0
ENV AGENT_RUNTIMES_PORT=8000
ENV AGENT_RUNTIMES_WORKERS=4
CMD ["agent-runtimes", "serve"]
```

```yaml
# Kubernetes ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: agent-runtimes-config
data:
  AGENT_RUNTIMES_HOST: "0.0.0.0"
  AGENT_RUNTIMES_PORT: "8000"
  AGENT_RUNTIMES_DEFAULT_AGENT: "crawler"
```
:::
