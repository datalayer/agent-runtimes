# Agentspecs

Agent Runtimes uses the [Agentspecs](https://github.com/datalayer/agentspecs) repository
as the source of truth for:

- Agents
- MCP servers
- Skills
- Environment variables

These specs are cloned locally and then compiled into the runtime catalogs used by
Agent Runtimes.

For the public platform docs and broader Agentspec context, see [datalayer.ai/docs](https://datalayer.ai/docs).

## Clone and Generate

From the repository root:

```bash
make specs
```

This command:
- Clones the agentspecs repository into ./agentspecs, or fetches it and
  fast-forwards it, on `AGENTSPECS_BRANCH` (`feat/apps-next` unless said)
- Generates Python and TypeScript catalogs for agents, MCP servers, skills,
  backend tools, frontend tools and env vars

**Backend tools and frontend tools.** `agentspecs/backend-tools` holds the tools
that run on the runtime, in Python (`agent_runtimes/specs/backend_tools.py`,
`src/specs/backendTools.ts`: `BackendToolSpec`, `BACKEND_TOOL_CATALOG`);
`agentspecs/frontend-tools` the sets of tools the page runs. An agent, an
application and a Frame name the first under `backend_tools` (`backendTools`),
the second under `frontend_tools`, and so does a request creating an agent
(`backend_tools` / `backendTools` on `POST /api/v1/agents`). The old `tools`
field is refused wherever a spec or a request is read, never read as the new one.

The MCP server, skill, backend tool and frontend tool generators check the marks of
each entry first, by `agentspecs.marks` imported from the clone: an icon that
does not say its package (`<package>:<name>`, the package
`@datalayer/icons-react` or `@primer/octicons-react`) or a missing emoji stops
the generator, naming the entry. See [Chat — Marks](../chat#marks-whose-a-tool-is).

## Using a Local Agentspecs Checkout

If you already have agentspecs checked out elsewhere, copy or symlink it to
./agentspecs before running make specs.

## Where Specs Are Used

The generated catalogs are written under `agent_runtimes/specs/` (Python) and
`src/specs/` (TypeScript):

- agent_runtimes/specs/agents/ · src/specs/agents/ (agents, subfoldered)
- agent_runtimes/specs/teams · src/specs/teams
- agent_runtimes/specs/skills.py · src/specs/skills.ts
- agent_runtimes/specs/tools.py · src/specs/tools.ts
- agent_runtimes/specs/frontend_tools.py · src/specs/frontendTools.ts
- agent_runtimes/specs/envvars.py · src/specs/envvars.ts
- agent_runtimes/specs/ui.py · src/specs/ui.ts (the UI plugins and the catalog of visual components) and agent_runtimes/specs/ui_renderers.py · src/specs/uiRenderers.ts (the UI renderers): see [UI plugins and Components](./ui.mdx)
- agent_runtimes/mcp/catalog_mcp_servers.py · src/specs/mcpServers.ts
- agent_runtimes/specs/decisions.py · src/specs/decisions.ts (how an agent decides: the model asked typed decisions, the question types, the limits; an agent names one with `decisions: jev:0.0.1`, which brings the `decide` tool)
- plus models, memory, policies (which the Guards extend), evals, events,
  notifications, outputs, personas, strategies, triggers, benchmarks — one
  catalog each, same pattern

## What You Can Define in an Agent Spec

Agent specs are not just static prompts. They define runtime behavior across UX,
workflows, controls, programmatic tooling, and delivery.

### A Plugin's Tools

A [Reactor](https://reactor.datalayer.tech) plugin's tools are declared *by
the plugin*, and none of them needs a spec in this repository — not the
commands a person runs from the palette, and not the reading and writing of
the plugin's data either.

The plugin contributes one `AgentTools` bundle to the reactor it is mounted in
([reactor.datalayer.tech/agent-tools](https://reactor.datalayer.tech/agent-tools)):
one entry per command an agent may call, with the name the model uses, the
command id, a description and the argument's JSON Schema. A command answers
with a value, and that value is the tool's result — so "list the decks" is a
command that returns the list, in the same registry as "next slide". The Loop
reads every mounted plugin's bundle (`useAgentCommandTools`) and hands the
agent one client tool per command, executed with `reactor.executeCommand` on
the page the person is looking at; the plugin saves to its server when it was
given one. The agent spec names nothing:

```yaml
# agentspecs/agents/worker-decks.yaml
tools: []
frontend_tools: []
```

The decks plugin is the worked example: `decks_list_decks`, `decks_get_deck`,
`decks_create_deck`, the per-slide edits and `decks_delete_deck` are its
commands as much as `decks_open` and `decks_present`, and its Python half
serves the same bundle from `GET /plugins/agent-tools` so a server can learn
them too. A plugin with a richer in-page implementation of a tool contributes
it under the same name, and the chat lets it win.

### Harness and Runtime Engine

Two fields, one after the other, say what runs an agent:

- `harness`: which agent program turns its loop. `pydantic-ai` (the default)
  and `vercel-ai` are built in; any other value is a coding agent of the
  harness catalogue, driven over ACP behind the Shield (see
  [Harnesses](../harnesses)).
- `runtime_engine`: what runs and hosts that program. Every agentspec says it,
  on the line after `harness`, and the generator refuses one that names none
  or another:
  - `datalayer`: a Datalayer agent runtime, from the platform's pools or
    started on your own machine (`agent-runtimes serve`). Every agent of the
    catalogue but two.
  - `kagent`: [kagent](../integrations/kagent). The agent is a kagent `Agent`
    whose `Harness` runs `agent-runtimes serve --target kagent` behind the
    kagent bridge, reached through kagent's A2A gateway at
    `/agents/{namespace}/{name}`; each conversation is a session actor of
    [Agent Substrate](../integrations/agent-substrate), suspended when idle
    and resumed on the next message. It takes the `pydantic-ai` harness only.
  - `agentcore`: [Amazon Bedrock AgentCore](../integrations/agentcore)
    Runtime, in the AWS account of the organization that launches it. The
    agent-runtimes image serves the agentspec (`agent-runtimes serve --target
    agentcore`) as an AgentCore agent runtime, which AgentCore starts on each
    invocation and bills to that account. It takes the `pydantic-ai` harness
    only. The catalogue's AgentCore agent is `worker-steward-aws`.

The spec's engine is the default, not a rule: a launch may run the agent on
another engine (`runtime_engine` on `POST /runtimes`, which Datalayer's
"Where it runs" sends when an agent is launched or an application deployed).
The platform checks the launch's engine as it checks the spec's: one of the
three, one that can run the agent's harness, and for `agentcore` an
organization with its AWS connection. What a launch ran on is on the runtime's
record and on the usage the platform records for it (`runtime_engine`), and
the platform's usage lists kagent's apart.

```yaml
# agentspecs/agents/example-kagent.yaml
id: example-kagent
model: "bedrock:us.anthropic.claude-sonnet-4-6"
harness: pydantic-ai
runtime_engine: kagent
sandbox_variant: eval
```

The generated catalogues carry it: `Agentspec.runtime_engine` in Python
(`datalayer` by default for an agent built in code), `runtimeEngine` in
TypeScript, with `RUNTIME_ENGINES`, `RUNTIME_ENGINE_LABELS` and
`RUNTIME_ENGINE_HARNESSES`. `RuntimesClient.create(runtime_engine=...)` in
Python and `runtimeEngine` on a runtime's creation in TypeScript send a
launch's own engine.

### UX Patterns and Protocol-Oriented Agents

Use transport and UI configuration in specs to power GenUI experiences and
protocol-targeted agents (AG-UI, A2UI, ACP, Vercel AI, A2A).

### Interactive and Triggered Workflows

Specs can run interactively (chat-driven) or as event/schedule-driven workflows.

- `trigger`: Defines schedule/event execution and startup prompt behavior.
- `pre_hooks` / `post_hooks`: Lifecycle setup/teardown in sandbox.
- `tool_hooks`: Tool lifecycle hooks using pydantic-ai names:
	- `before_tool_execute`
	- `after_tool_execute`
	- `on_tool_execute_error`
	- `deferred_tool_calls`

### Identity and Controls

Specs can include controls such as tool approval workflows, guardrail-oriented
runtime behavior, and monitoring-friendly metadata (used by snapshots/streams).

### Programmatic Tooling (Sandbox, Codemode, Skills)

- `sandbox_variant`: Selects execution sandbox (`eval` or `jupyter`). `browser`
  is Pyodide in the page: an agent that names it runs in the page only, and
  `POST /api/v1/agents` refuses it on a runtime (422, *… runs its code in the
  browser: it is not started on a runtime.*).
- `enable_codemode` and codemode config: Enables MCP-discovery + programmatic composition.
- `skills` / `enable_skills`: Enables reusable skill execution.

### Memory

- `memory`: the agent's durable memory — `mem0` (on Datalayer, kept in
  PostgreSQL under the person and the agent's id) or `agentcore` (Amazon
  Bedrock AgentCore Memory in your own AWS account). `memory_config` gives the
  backend what it needs; for `agentcore`, the memory resource to use:

  ```yaml
  memory: agentcore
  memory_config:
    memory_id: my_memory-AbCdEf1234   # or AGENT_RUNTIMES_AGENTCORE_MEMORY_ID
    region: us-east-1                 # or AWS_REGION
    namespaces: ["/facts/{actorId}"]  # optional: read from the memory's strategies
  ```

  The agent's turns are kept as events of the person (the actor, their account
  id) in the agent's session (its spec's id); `search_memory` reads the
  long-term records AgentCore's strategies extract, in namespaces with
  `{actorId}` filled in. A memory that is not named is refused when the agent
  is created, never replaced by another store; a namespace without `{actorId}`
  is refused before anything is read from it.

### Outputs and Notifications

For triggered workflows, specs can define delivery behavior:

- `notifications`: Email/slack/webhook style delivery channels and recipients.
- output-oriented fields in workflow specs to control the shape/destination of generated artifacts.

### Real-Time Collaboration and Multi-Agent Teams

Specs can represent single agents or orchestrated teams.

- Team/orchestrator specs coordinate specialized workers.
- Collaboration is surfaced through runtime protocols (especially ACP/A2A).
- A sequential or parallel team runs as an orchestration. Delegating it
  (`executions.delegate`, with the team's id as the agent and `datalayer` as
  the protocol) roots a tree on its supervisor, runs each member as a child in
  the order `depends_on` gives, and has the supervisor answer from what they
  produced. Each seat is named `team:<team>/<seat>`. A seat that references an
  agentspec runs on it; one that does not runs on an agentspec built from its
  own goal, model, tools and MCP server (`agent_runtimes.orchestration.teams`).
  In a team whose supervisor routes the work, the supervisor is registered with
  the members as its A2A subagents, each a seat it asks the control plane for,
  and is told the team's routing instructions. An agent can be created with
  such subagents in place of its agentspec's (`subagents` on the create
  request).

## Minimal Example Fragments

```yaml
id: generate-weekly-reports
trigger:
	type: schedule
	cron: "0 8 * * MON"
	prompt: "Run the scheduled workflow and produce the configured deliverable."

sandbox_variant: jupyter

skills:
	- report-generation

notifications:
	email: "team@acme.com"
```

```yaml
id: example-tool-approvals
tool_hooks:
	before_tool_execute:
		- function: agent_runtimes.integrations.tool_policy:evaluate_tool_request
	after_tool_execute:
		- python: |
				print("success", payload.get("tool"), payload.get("status"))
	on_tool_execute_error:
		- python: |
				print("error", payload.get("tool"), payload.get("error_type"))
	deferred_tool_calls:
		- python: |
				print("deferred hook invoked")
```

```yaml
id: comprehensive-sales-analytics
description: Multi-agent team with orchestrator + specialists

mcp_servers:
	- postgres
	- slack

skills:
	- data-quality
	- forecasting
```
