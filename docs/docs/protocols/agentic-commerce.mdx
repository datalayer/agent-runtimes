# Agentic Commerce Protocol: a checkout, approved once

Agent Runtimes speaks the
[Agentic Commerce Protocol](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol)
(OpenAI, Stripe) **2026-04-17** as a buyer, in Python and TypeScript, over
REST. In code it is `agentic_commerce`, never `acp`: `acp` is the Agent
Client Protocol, an editor protocol Agent Runtimes also speaks.

| | Python | TypeScript |
| --- | --- | --- |
| Package | `agent_runtimes.protocols.agentic_commerce` | `@datalayer/agent-runtimes/lib/protocols/agentic-commerce` |
| Models | generated from `spec/2026-04-17/json-schema/schema.agentic_checkout.json` by datamodel-code-generator 0.34.0 | generated by json-schema-to-typescript 15.0.4 |
| Plugin | `agent-runtimes.protocols.agentic-commerce` | `AgenticCommercePlugin` |

No maintained client exists from the specification's authors (the
`agentic-commerce-protocol` package of PyPI and npm is a third party's), so
the models are generated here, pinned to the dated version:
`scripts/codegen/generate_agentic_commerce.sh [VERSION]` regenerates both.

## A purchase is a proposal

As with [UCP](./ucp), nothing is bought in one call: a `ready_for_payment`
session becomes an exact, revisioned proposal the person approves, completed
once, the proposal's id its `Idempotency-Key`:

```python
client = AgenticCommerceClient(
    seller="https://outfitters.example",
    credentials=credentials_of(platform),
    extensions=declared_extensions(platform),
)
session = await client.create_checkout([{"id": "socks", "quantity": 2}], "usd")
session = await client.update_checkout(session["id"], {"buyer": {"email": "ana@example.com"}})
proposal = await client.propose_completion(session["id"])
order = await client.complete(
    proposal,
    approver=approver_of(platform),
    payment=payment_data_of(platform),
    store=proposal_store_of(platform),
)
```

Every request carries `Authorization: Bearer` (the agent's credential with
that seller, from the host), `API-Version: 2026-04-17`, and on every POST an
`Idempotency-Key`.

**One item per unit.** The 2026-04-17 schema's `Item` has no `quantity` and
forbids other fields, while the specification's examples send one; the
schema is followed: a quantity of two is the item twice, and the seller
counts them.

## The plugin and its points

| Point | Default | What a host contributes |
| --- | --- | --- |
| `agentic_commerce.approver` | none: nothing is bought | the same approver it gives `ucp.approver` |
| `agentic_commerce.paymentData` | none | a delegated payment token (`spt`) from custody |
| `agentic_commerce.credentials` | none | the agent's bearer with each seller |
| `agentic_commerce.proposalStore` | `memory` | a store shared by its processes |
| `agentic_commerce.extension.discount` | none | the discount extension |
| `agentic_commerce.extension.other` | none | any other extension, by name |

An agent declares in `capabilities.extensions` only the extensions
contributed to these points (`declared_extensions`); the seller answers
with those it activates.

## The test seller and the example

`agent_runtimes.protocols.agentic_commerce.merchant.ExampleOutfitters` is a
local seller (discovery, checkout sessions, the discount extension), holding
an agent to `Authorization`, `API-Version` and `Idempotency-Key` (`409` on a
reused key with another body); every answer is validated by the generated
models.

## Example

Runs locally, against the test seller above, in one process with no network
and no model (example EX-05):

```bash
python examples/protocols/agentic_commerce/checkout.py --yes
```

It prints the seller's discovery (`outfitters.example speaks the Agentic
Commerce Protocol 2026-04-17`, the `discount` extension), a session
`not_ready_for_payment` until the buyer's email is given, the `WELCOME10`
discount applied (`ready_for_payment`), the exact purchase to approve (*Buy
2 × Wool socks at outfitters.example for USD 29.16*), the order once bought,
and the same proposal refused a second time. Without `--yes` it asks you to
approve. The TypeScript client (`agenticCommerce.unit.test.ts`) runs against
a seller answering with the shared fixture.

## Conformance

Agentic Commerce `2026-04-17`. `agentic_commerce/fixtures/session.json` (a session, the discovery document, the revision digest) is read by `test_protocols_agentic_commerce.py` and `agenticCommerce.unit.test.ts`; both validate with models generated from the same JSON Schema.
All protocols side by side: [Conformance](./agent-protocols#conformance).

## What never reaches a model

The payment token and the bearer go to the seller and nowhere else:
`session_summary` and `proposal.summary()` are what an agent sees, and the
tests check that neither secret is in them.
