# Authenticating to a Runtime

A runtime is one person's: it runs their agent, holds their connections and spends their credits. Its routes answer accordingly. This page says which routes need a credential, which credentials a runtime takes, and how a client sends one.

## The four kinds of routes

Every route of a runtime is one of four kinds. A route that is not listed as one of the first three is the owner's: that is the default, and what a route added tomorrow is until somebody lists it.

| Kind | Routes | Who is answered |
|------|--------|-----------------|
| **Public** | `GET /health`, `/health/live`, `/health/ready`, `/health/startup`; the built pages (`/agent`, `/static/*`, `/html/*`); what a page reads of an application's plugins (`GET /api/v1/apps/{app_id}/plugins/state`, `/plugins/frontend-extensions`, `/events/stream`, `/reactor-extensions/...`) | Anybody. A health answer says nothing of the sandbox's credentials to a caller that did not prove itself. |
| **Application** | `/api/v1/apps/**`, an application's agent over A2A (`/api/v1/a2a/agents/{agent}/**`), and the chat's reads of its models (`GET /api/v1/configure`, `/configure/models`) on a runtime that serves an application | Whoever the application's deployment allows. Each route verifies its caller itself: a visitor's, an embed's, a host's, a member's or the principal's token, and nothing for what a public application shows (its agent card, its chat for visitors). |
| **Self-proving** | `POST /api/v1/agent/handoff/exchange`, `GET /api/v1/mcp/auth/callback`, `POST /api/v1/identity/oauth/token` and `/userinfo`, `/api/v1/agents/{agent_id}/webhook`, and the contracts of the platforms a runtime is started for (`/ping`, `/invocations`, `/ws`; `/ate/wakeup`, `/ate/identity`) | A caller that holds the one-use code, the state or the declared source the route checks. |
| **Owner** | Everything else: agents, configuration, MCP servers, the sandbox, memory, checkpoints, history, the chat transports (`/vercel-ai`, `/ag-ui`, `/acp`, `/a2a` of an agent that serves no application), `/api/v1/runtime/status`, `/docs`, `/openapi.json`, and every websocket other than the application's | A caller that proves the runtime is theirs. |

## Proving the runtime is yours

A call to an owner's route presents one of these tokens, **from the machine itself as from anywhere else**. Since 1.8.9 an address proves nothing: on a person's own machine a web page open in their browser reaches the runtime's loopback too, so a call from `127.0.0.1` without a token is no longer taken as the owner's.

- **The owner's Datalayer token.** The token the person is signed in with (or an API key of theirs), which the platform accepts and which names the account the runtime is assigned to. On a Kagent agent's runtime, which is given nothing of its owner's, the account it is assigned to is the one whose reservation it is: the runtime asks IAM, with the caller's own token, whether that reservation is theirs, once, and remembers the answer. On a runtime launched for a deployment, the deployment's owner proves it too, the same way (since 1.8.12): with the key IAM mints for them to run the deployment's runtime, which names that deployment (what keeps an always-on application running sends it), or with their own token, when ai-agents, asked with it, answers the deployment as theirs. Asked once, remembered. An application's token, a visitor's and anybody else's prove nothing.
- **The runtime's own token.** On a Datalayer runtime, the token of its sandbox, which the platform gives the owner with the runtime's record (`token` in `GET /api/runtimes/v1/runtimes/{uid}`). On a runtime started on your machine, the token it prints when it starts (see below).

Another site's page on the loopback (an `Origin` that is neither this machine's nor Datalayer's, or `Sec-Fetch-Site: cross-site`) is refused with `403` in both modes, whatever forwarding header it sends: a forwarding header is only a header, and the loopback is still its peer. A call is taken as passed on by a proxy only when its peer is not the machine itself.

Two callers on the loopback need no token, each for what it alone does:

- **The companion beside the runtime**, by the pod's secret, on a runtime launched for a deployment.
- **A skill's script in the sandbox**, which holds no credential, on the few routes skills call: the runtime's agents (`GET /api/v1/agents`), an agent's memory (`/api/v1/agents/{agent_id}/memory`, `/memory/search`, `/memory/{memory_id}`), who the runtime runs for and its agent's events (`/api/v1/owner`, `/api/v1/owner/events`), `POST /api/v1/spaces/files`, `POST /api/v1/configure/mail`, `POST /api/v1/library/items/{uid}/publish`, and the sandbox's tool calls (`/api/v1/mcp/proxy/*`). Only from the loopback, passed on by no proxy, and made by no browser: a request that carries an `Origin` or fetch metadata is a page, and a page is no skill. A harness's lent toolsets and model relay (`/api/v1/mcp/lent/*`, `/api/v1/inference/relay/*`) are reached from the loopback by the handle the harness was given, which the route asks. On a runtime that serves an application, these answer only while code the agent was let run is running.

### A runtime on your machine

`agent-runtimes serve` prints the runtime's token once on the terminal when it starts (never to its log):

```text
This runtime's token (send it as 'Authorization: Bearer <token>', or as
the 'token' query parameter of a websocket; set AGENT_RUNTIMES_TOKEN to
choose it):

    3q2-…

    curl -H 'Authorization: Bearer 3q2-…' http://127.0.0.1:8765/api/v1/agents
```

Set `AGENT_RUNTIMES_TOKEN` before starting it to choose the token yourself, as a client that starts a runtime does: the `agent` CLI draws one for the runtime it starts and signs every call with it. Local scripts and tools that call a runtime must send its token like any other client.

Send either token as a bearer:

```http
GET /api/v1/agents HTTP/1.1
Authorization: Bearer <token>
```

Jupyter's scheme is taken too (`Authorization: token <token>`). A browser opens a websocket without headers of its own, so a websocket carries the token in its `token` query parameter:

```text
wss://<runtime>/api/v1/configure/sandbox/ws?agent_id=default&token=<token>
```

A token of another kind proves nothing on an owner's route: an application's visitor, embed, host or principal token reaches the application's routes, which verify it themselves, and nothing else.

In TypeScript, `runtimeAuthHeaders(token)` and `runtimeSocketUrl(url, token)` (exported from the package's `hooks/ownRoutes`) build the header and the websocket's address, and send nothing when no token is held. The hooks, adapters and panels that call a runtime take the token as an optional `authToken`: a page on the same machine as its runtime passes the runtime's token too.

## What a caller that proved nothing is told of the sandbox

`GET /health/startup`, `GET /api/v1/runtime/status`, `GET /api/v1/configure/codemode/status`, `GET /api/v1/configure/agents/{agent_id}/spec` and the frames of the `/api/v1/configure/sandbox/ws` websocket describe the sandbox: its variant, its address, its kernel, whether it runs. The sandbox's token is in those answers only for a caller that proved the runtime is theirs; for anybody else the `jupyter_token` key is not there, and an address carries no `token` parameter. The monitoring stream and the skills' catalogue never carry it.

A client that needs the token to open a kernel connection reads it from the platform's record of the runtime, or sends its credential on the call that describes the sandbox.

## Log, then enforce

The lock runs in one of two modes, set by `AGENT_RUNTIMES_ACCESS_MODE` and read once when the runtime starts:

| Mode | A call to an owner's route that proves nothing |
|------|-----------------------------------------------|
| `log` (the default) | Is served as before, and said in one line of the runtime's log and on one OpenTelemetry counter. A call from the machine itself without a token is still told the sandbox's token, unless it comes from another site's page. |
| `enforce` | Is refused: `401` with a sentence over HTTP, a denial at the handshake for a websocket. |

Any other value stops the runtime from starting: it never takes a setting it cannot read for either mode.

The log line names the route by its template, never by the path that was asked, and never carries a token or a query:

```text
ACCESS unproven mode=log action=served method=GET route=/api/v1/agents/{agent_id}/memory reason=no-credential agent=Mozilla/5.0 origin=example.com referer=example.com source=ingress
```

- `reason` is why the call proved nothing: `no-credential`, `loopback-no-credential` (a call from the machine itself that sent no token: a local client to give the runtime's token), `token-refused` (the platform does not accept it), `another-account`, `application-token` (a token for the application's routes), `owner-unknown` (the runtime is not assigned yet), `unverifiable` (the platform could not be asked: on a Kagent agent's runtime before 26 November 2026, its egress did not reach IAM) or `strangers-page` (another site's page on the loopback, refused in either mode).
- `agent`, `origin` and `referer` are the client's product and the hosts a browser names; `source` is where the call entered: `loopback` (its peer is the machine itself, whatever headers it sends), `ingress` (a proxy passed it on) or `cluster`.
- The line is written at most once a minute for one route, reason and caller. The counter `agent_runtimes.access.unproven` counts every call, with the same attributes.

Run a deployment in `log` mode first, fix the clients the log names, and switch to `enforce` once it has stayed quiet.
